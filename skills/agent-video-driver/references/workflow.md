# 完整工作流程

八个阶段, 每个阶段都要落一个可检查的产物再进下一阶段.
阶段 1 到 3 与用户之间的往返次数由确认模式决定, 见 SKILL.md 第一节.
两个门与交互纪律 (交付先于提问, 静态样图只管配色与版面, 进度按实测值汇报, 改需求先算连带代价) 也见 SKILL.md 第一节, 本文件只写每个阶段的具体动作与产出物.

```
0 探测环境 -> 1 简报与提示词 -> 2 内容与文案 -> 3 风格与分镜
  -> 4 配乐先行 -> 5 分段渲染 -> 6 编码封装 -> 7 客观验收
```

## 阶段 0, 环境探测

跑 `python scripts/check_env.py`, 它会报告:

- FFmpeg 与 FFprobe 是否在 PATH, 是否带 libx264 与 aac 编码器
- Python 版本与 numpy, Pillow 是否可用
- 中文字体是否存在 (msyhbd.ttc 黑体粗, msyh.ttc 常规, consola 等宽)
- 磁盘可用空间 (3000 帧 PNG 约需 600MB)
- 沙箱限制提示: multiprocessing 命名管道, 子进程 Wait-Process
- 渲染路线可用性: Python 子进程管道能力, 以及浏览器能否启动

探测不过关就不要往下走, 把缺失项和影响告诉用户让他决策.
浏览器不可启动时画面只能走 Python + Pillow 路线, 这是本技能的默认路线, 不影响交付.

产出物: 一份探测报告, 缺失项与影响清单.

## 阶段 1, 简报与提示词

按 `references/prompt-scaffolding.md` 建两份文件:

- `prompts/brief.md`: 全片唯一的一份背景, 照 `templates/brief.md` 填, 每完成一个阶段更新一次
- `prompts/<阶段名>.md`: 每个阶段一份, 照 `templates/stage-prompt.md` 的七模块填

`role` 与 `task` 与 `check` 每阶段必写, `context` 由简报承担, `specs` 与 `style` 与 `avoid` 按需.
填好的提示词要与该阶段的产出一起给用户看; 用户改了提示词就从改后的版本重做该阶段.

产出物: `prompts/brief.md` 与当阶段的提示词文件, 且用户已过目.

## 阶段 2, 内容与文案

两段式, 不要跳步:

1. **研究与核查**: 先判题材形状 (时间线, 因果链, 由浅到深, 对照, 一问一答, 单个故事), 再联网查证, 把知识节点与来源链接写进工作目录. 找不到可靠出处的直接删掉
2. **文案编排**: 改写成"一屏一句"的屏文案表 `script.md`, 照 `templates/screen-script.md` 填

判定规则与汇报格式见 `references/content-and-rights.md`, 开场语法与单屏字数见 `references/narrative.md`.
按时长给两到三个"讲几个点"的方案让用户选一个, 再往下走; 覆盖度定错了会让分镜整体重排.

产出物: 带出处的知识节点清单, 删改汇报, `script.md`, 以及用户选定的覆盖方案.

## 阶段 3, 风格与分镜

1. **定配色与风格**: 先按 `SKILL.md` 门一把配色问清楚, 给三到五个差别看得出来的色相方向让用户挑, 或请用户直接给主色与底色, 拿到明确的色值再往下; 用户没有点名风格或参考片时再抽签 (`python scripts/style_lottery.py --seed <种子>`), 抽到哪张做哪张; 用户点名了风格或参考片就跳过抽签, 直接按 `references/styles.md` 对应的那一节走, 配色仍要用户确认
2. **出样图**: 把配色与抽到的牌合成一个**配色与风格组合方向**, 出**两张**样图: 一张标题卡, 一张该方向最典型的演示屏. 只用标题卡或声明卡不行, 那是全片最特殊的一屏, 判断不了后面的演示元素; 两张都要附上底色与强调色的十六进制值. 出完把两张样图的**文件路径**交给用户, 等回执认可配色与风格, 之后才写分镜
3. **排拍表**: 跑 `python scripts/timing.py script.md --bpm <BPM> --bars <小节数> --anchor <屏号:小节号>`, 产出 `temp/plan.json` 与 `temp/plan.md`; 屏号用跨幕连续编号, 小节号从 1 开始; 排不下时它会报清缺口, 此时精简文案或调大总小节数
4. **写分镜**: 用 `templates/storyboard.md` 填一张表, 必须包含:

| 字段 | 说明 |
|:---:|:---|
| 时长与帧率 | 例 108.000s / 30fps / 1920x1080 |
| BPM 与小节 | 例 100 BPM, 拍 0.6s, 小节 2.4s, 共 45 小节 |
| 拍表来源 | 本技能合成的配乐, 或用户提供音乐经 `beats.py` 测出的拍表 |
| 段落表 | 每段的起止秒, 起止小节, 段内要演示的内容, 元素入场拍 |
| 贯穿线索 | 例 全片左上角的年份戳随进度推进, 已访问节点变色 |
| 配色 | 底色与强调色 1 到 4 的十六进制值, 以及来源 (用户指定或兜底色板) |
| 风格 | 抽到的牌 id 与名称, 加上字体搭配; 牌面落在 `STYLE.md` |
| 配乐音色 | 例 毛毡钢琴 + 慢起 pad + 正弦低音, 不要噪声镲 |
| 交付文件名 | 含主题, 时长, 版本 |
| 作者署名 | 默认不加, 要加就写明文案 |

把这张表发给用户, 同时给出启动确认门的三项代价 (token, 中间帧, 会话独占), 得到明确同意后才进入阶段 4.

分段经验值:

- 30s 片: 6 到 8 段, 每段 4 到 5 秒, 每段一个演示点
- 90s 以上: 8 到 12 段, 每段 8 到 14 秒, 每段 2 到 4 个演示点
- 段落边界必须落在小节线上, 段落长度取 2 到 6 个小节的整数倍
- 每段内部至少有一次数值或图形变化, 纯静态段落不要超过 2 秒
- 任意两段的内部结构不得完全相同
- 关键句 (揭晓, 反转, 末屏) 落在音乐能量变化的那一小节第一拍

产出物: `temp/plan.json`, `storyboard.md`, `STYLE.md` (抽签或点名定下的牌面), 两张带色值的样图 (标题卡与典型演示屏) 与它们的文件路径, 用户的回执, 以及同意开始的确认.

## 阶段 4, 配乐先行

先出 `audio/score.wav`, 再写画面. 理由:

- 画面切点必须等于配乐切点, 音乐先定就锁死了时间轴
- 配乐生成只要几十秒, 画面渲染要几分钟, 早发现问题早改
- 配乐段落表就是画面的段落表, 两份时间轴来自同一个常量

```
python scripts/orchestra.py <时长秒> <BPM> <输出文件名> <切点逗号分隔>
```

切点取 `plan.json` 的幕边界, 不要另写一份.
用户自备音乐时改用 `python scripts/beats.py <音频> --json temp/beats.json` 反推拍表, 再用它对齐画面.

产出后立刻跑客观检查 (见 `verification.md` 的音频部分), 拍点能量比与频段占比达标才继续.

产出物: `audio/score.wav`, `check_audio.py` 的完整报告, 后续可选的 `audio/sfx.wav`.

## 阶段 5, 分段渲染

写一个场景模块 (照抄 `templates/scene_module.py`), 结构固定为:

1. 顶部常量: 时长, BPM, 调色板, 字体, 以及段落边界来源 (`temp/plan.json` 或常量数组)
2. 每个段落一个函数 `s_xxx(c, t)`, 内部用 `lb = (t - 段起点) / BEAT` 计算局部拍数
3. 所有入场用 `beat_on(lb, k, d)` 触发, 不要用 `seg(t, a, b)`
4. 一个 `pick(t)` 按区间映射到段落函数, 区间左闭右开
5. 用 `canvas.render_range(pick, a, b, cam)` 渲染

一个场景函数对应**一幕**, 不是一屏. 幕内有多屏时, 屏序分支必须写在场景函数内部 (模板给了 `sub(t)`, 返回当前是这一幕的第几屏, 屏起点优先取 `temp/plan.json` 里该幕各屏的 `t`); 不分支的话同幕第二屏会被第一屏的画法整个盖掉, 上屏内容永远不出现, 而且不报错.

每个段落内部的实现顺序 (按这个顺序做, 返工最少):

| 步骤 | 做什么 | 先确认什么 |
|:---:|:---|:---|
| 1 | 底板与环境光: 背景三色, 环境光带, 网格或地平线 | 用单帧确认整体亮度对, 不是"大概差不多" |
| 2 | 主体: 大字, 图形, 坐标轴, 主结构 | 用单帧确认位置与大小, 原点落在该落的地方 |
| 3 | 运动: 入场, 缓动, 错帧 | 抽多帧看时间轴, 单帧看不出缓动对不对 |
| 4 | 版面家具: 章节标签, 时间码, 进度线 | 最后加; 它是全片最容易喧宾夺主的东西 |

- 每一档都要先渲一帧或一小段再往下, 四档一起写完再渲, 出问题时定位成本高得多
- 单帧用 `python scene_module.py at <段号>:<拍号>`, 一段多帧用 `python scene_module.py stills <段号>`, 两个模式的说明见 `templates/scene_module.py`
- 版面家具的位置先按 `visual-engine.md` 的四角纪律分配好, 一个角落只放一样东西

渲染顺序建议:

1. 先跑 `probe` 出 20 到 30 张代表帧, 逐张做字符图核对, **并读它打印的字形审计报告**: 代表帧只覆盖部分时刻, 但能把大部分缺字形问题提前暴露出来
2. 再渲染开头约 10 秒的**带音轨**连续预览, 把成片文件路径明确告诉用户, 等用户看完给出回执, 之后才提问或进入下一决策; 这一步能暴露单帧看不出的转场与音画偏移, 静态样图代替不了
3. 改到构图无误后, **走一次合成确认门**: 探测资源, 把限额与风险报给用户, 拿到同意再全量渲染
4. 用 `python scene_module.py plan` 拿到建议的进程数与帧区间, 每个区间一条命令, 开独立进程各跑各的
5. 每个区间渲完都会打印自己那一段的字形审计报告, 把"回退链也找不到字形"的项全部处理掉再进下一阶段

合成确认门的内容:

```
python scripts/resources.py --for render --frames 3240
```

它给出核数, 当前负载, 可用内存, 目标盘剩余空间, 建议的并行进程数, 以及是否建议拦截.
判定为空间不足或负载过高时不要开工, 先向用户报告并让他决策 (清理磁盘, 等机器空闲, 或缩短片子).
全量渲染的进程数不要超过建议值, 机器空闲时用户可以要求提高.

产出物: 代表帧字符图核对记录, 开头预览成片与它的文件路径, 用户的回执, 帧序列, 字形审计报告, 以及一份资源探测报告.

## 阶段 6, 编码封装

这一步也是重活, 编码前同样要单独走一次合成确认门. 分两条路线, 先按片的体量选一条:

| 路线 | 脚本 | 什么时候用 |
|:---:|:---|:---|
| 一次编完 | `scripts/assemble.ps1` | 帧数不多的短片, 中途中断重来也不心疼 |
| 分批编码 | `scripts/assemble_core.py` | 长片, 或用户要求分批, 或需要进度可见与断点续跑 |

两条路线的确认门, 限额施加与验收口径完全一致 (退出码 3 等待二次确认, 4 探测判定应拦截, 5 真峰不合格), 区别只在视频流是不是切成几批编.

```
python scripts/resources.py --for encode --frames 3240 --out-dir out
# 一次编完: 只探测
powershell -ExecutionPolicy Bypass -File scripts\assemble.ps1 -Frames temp\frames_proj -Audio audio\score.wav -Out out\成片.mp4 -ProbeOnly
# 分批: 只探测
python scripts/assemble_core.py --frames temp/frames_proj --audio audio/score.wav --out out/成片.mp4 --batches 8 --probe-only
```

探测命令只打印确认门, 不做任何编码. 把它的输出报给用户, 拿到同意后再正式跑 (ps1 加 `-ConfirmAssembly`, py 加 `--yes`).
只装了 Windows PowerShell 5.1 的机器不要写 `pwsh` (不存在), 并且务必带 `-ExecutionPolicy Bypass`, 否则默认执行策略会拦下未签名脚本.
不带确认开关时脚本只打印确认门并退出 3, 表示"正在等待用户二次确认"; 探测判定空间不足或负载过高时脚本会拒绝开工, 要强行开工必须显式加 `-Force` (py 是 `--force`), 并把理由告诉用户.

流程:

```
1 帧序列 -> H.264 (libx264, CRF 18 到 20, 按探测建议的 preset 与 -threads, +noise 轻颗粒)
2 视频流 + 配乐 WAV -> AAC 384k (-AudioBitrate 可调), loudnorm 归一到 -15 LUFS
3 -movflags +faststart, 输出到交付目录
4 从成片解码回来量真峰, 超过 -TruePeakCeiling (缺省 -1.0 dBFS) 判不合格并退出 5
```

音轨码率不要降到 256k: 瞬态密集的素材在 256k 下解码回来的真峰会冲到 0 dBFS 以上, 各档实测对照见 `verification.md` 的真峰一节.
限额由脚本自己施加: `-Threads` 缺省取探测建议值, `-Preset` 缺省按负载在 `slow` 与 `medium` 之间选, 并把自身进程优先级降到 `BelowNormal` 让子进程继承, 于是编码期间机器仍可正常操作.
对响度要求严格时打开 `-ExactLoudness` (py 是 `--exact-loudness`), 它用 "量测 `ebur128` 加精确增益加限幅" 的闭环替代单遍 `loudnorm`, 且不重渲画面.
若加了音效轨, 先跑 `scripts/sfx.py` 混出音效 WAV, 再与配乐一起混, 混完必须重跑响度验收.
编码后立即 ffprobe 核对时长与流信息.

### 分批编码的纪律 (用 `assemble_core.py` 时必读)

```
# 分批编码 (后端; 另开一个终端用前端看进度)
python scripts/assemble_core.py --frames temp/frames_proj --audio audio/score.wav \
    --out out/成片.mp4 --batches 8 --preset medium --yes
python scripts/assemble_progress.py --watch
```

- **只切视频流, 音频必须整条一次处理**: 集成响度只能在整条音轨上量测, 分成几段各自归一化会让响度验收失效
- 切片用 `-start_number` 加 `-frames:v`, 不要用 `-vf select`: `select` 是解码之后才丢帧, 每批都会把整段 PNG 全解码一遍, 实测慢一倍以上, 而且会把编码器的真实开销掩盖掉
- 各批的编码参数必须完全一致, 否则 `-c copy` 拼接会失败或损坏
- 拼接列表只写 basename 并与分段同目录: concat demuxer 是按列表文件所在目录解析相对路径的
- 后端每完成一批就原子写状态 JSON (缺省是脚本同目录的 `assemble_state.json`), 里面是配置快照, 批次表, 当前阶段, 已完成帧数与 pid; 前端只读轮询它画进度条, **前端不启动也不停止后端**, 启停权在用户手里
- 编码器缺省 `libx264` (CPU 路线, 画质与体积的标定口径). 要换硬件编码器就给 `-Encoder` / `--encoder` (例如 `h264_nvenc`), 脚本会把 preset 与 crf 映射过去; 但换编码器不是加开关, 换完必须重新量 PSNR, 换之前先跑 `python scripts/bench_encode.py` 对比耗时, 体积与 PSNR
- 中断 (Ctrl+C, 关机, 崩溃) 之后重跑同一条命令即从断点继续; 配置与上次不一致时脚本拒绝续跑并要求显式 `--restart`; `--redo N` 只重做指定批次
- **源帧改过就必须重编受影响批次**: 视频里是旧帧而磁盘上是新帧时, PSNR 验收会假性崩掉 (实测 5% 错配帧把 57dB 拉到 37dB), 所以 `--redo N` 是保证验收有效性的必要手段, 不是便利功能
- `-movflags +faststart` 让输出文件在整批编码完成前一直是 0 字节, 所以判断进度只能靠状态 JSON, 不能看文件体积

产出物: 交付成片, 流信息与响度实测值, 一份资源探测报告, 以及分批路线的状态 JSON (验收后连同 `temp/` 下的分段一起清理).

## 阶段 7, 客观验收

各项判据见 SKILL.md 第八节, 方法见 `verification.md`.
最后清理 `temp/` 下的帧序列, 只留成片, 配乐 WAV 与源脚本.

产出物: 验收记录表 (填进 `storyboard.md` 第七节), 清理后的交付目录.

## 附, 流水线模式 (设计草案, 尚未实现)

阶段 5 与阶段 6 现在是严格串行的: 全部帧渲完才开编码, 总时长约等于"渲染时长加编码时长".
渲染吃的是 Python 逐帧绘制, 编码吃的是 x264, 资源上并不冲突, 所以可以做成流水线: 渲染进程每完成若干帧就落一个批次完成标记, 编码进程轮询该标记, 发现新批次就立即编码并接到成片末尾.
本节只是设计草案, **技能当前没有实现这条路线**, 需要时再落地.

设计要点:

- **共用分批机制**: 与阶段 6 的分批编码共用同一套批次划分, 状态 JSON 与断点续跑逻辑, 不另起一套; 批次大小要让编码单批时间明显短于渲染单批时间, 否则编码会成为瓶颈
- **追加方式用"每批独立 mp4 最后统一 concat"**, 不要边编边改同一个 mp4: MP4 的 moov 原子在文件尾部, 原地追加必须整文件重写
- **必须保留一个最后统一混音的收尾步骤**: 集成响度只能在整条音轨上量测, 中途成片只能是"视频就绪, 音频待定"的状态
- **中途产物是未完成态**: 音画同步与全片响度都要等收尾之后才能验收, 这一点必须明确告知用户, 不要让用户以为中途文件就是成片
- 渲染与编码抢同一台机器的 CPU, 并行度不能取两边的建议值之和, 要按 `resources.py` 的限额重新分配, 否则比串行还慢
