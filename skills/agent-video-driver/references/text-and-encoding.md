# 字符集与乱码

视频任务里文本要经过三层, 每层都可能把字弄坏. 三层的病因与治法完全不同, 必须分开排查.

| 层 | 现象 | 病因 | 治法 |
|:---:|:---|:---|:---|
| 文件层 | 源码里的中文变成 `鍧愭爣绯` | 读写时按 ANSI/GBK 解码了 UTF-8 字节 | 一律用 Python 显式 `encoding='utf-8'` 读写 |
| 控制台层 | 打印报 `UnicodeEncodeError: 'gbk' codec` | Windows 控制台默认 GBK, 打印不了 `¥` 之类字符 | 设 `PYTHONIOENCODING=utf-8`, 或把字符写成 `\u00a5` |
| 渲染层 | 画面里出现空心方框 (豆腐块) | 字体里没有该字符的字形 | 渲染前做字形体检, 缺字形就换写法或换字体 |

## 一, 文件层

PowerShell 的 `Get-Content` 在部分环境按 ANSI 解码, 再用 `Set-Content` 写回就把中文永久写坏了. 本技能实际踩过: 用 `Get-Content` 切一段 py 源码再写出去, 中文全部变成 `鍧愭焺绯`.

规矩:

- 文本的读取, 切片, 改写一律用 Python, 不用 PowerShell 管道
- 显式写全 `open(path, encoding='utf-8')` 与 `open(path, 'w', encoding='utf-8', newline='\n')`
- 不要写 UTF-8 BOM. Python 3 能读带 BOM 的源码, 但 BOM 会污染 diff 与其他工具
- 判断是否被写坏: 出现 `鍧 愭 爣` 这类生僻字连排就是典型的 UTF-8 被按 GBK 解过

## 二, 控制台层

- `print` 含 `¥` `≈` `·` 等非 GBK 字符会直接抛 `UnicodeEncodeError`
- 治法是 `set PYTHONIOENCODING=utf-8` 再跑, 或者干脆在源码里写转义 `"\u00a5"`
- 反过来也要注意: PowerShell 回显中文乱码不代表文件坏了, 只说明回显用的不是 UTF-8. 用 Python 读一遍确认才是准的

### 反过来的一层: 读子进程的输出

同一个坑在**接收**方向也成立, 而且症状更隐蔽: `subprocess.run(cmd, text=True)` 在 Windows 上按系统代码页(GBK)解码子进程的输出, 而子进程打印的是 UTF-8 中文, 于是读线程直接抛 `UnicodeDecodeError`, 主进程拿到的是残缺结果或非零退出码.

```
# 错: 在中文 Windows 上解码子进程的 UTF-8 输出会炸
subprocess.run(cmd, text=True, capture_output=True)

# 对: 显式指定编码
subprocess.run(cmd, text=True, capture_output=True, encoding="utf-8", errors="replace")
```

- 自己写脚本调用本技能的其他脚本时, **一律显式给 `encoding`**; 不要依赖 `text=True` 的缺省值
- 症状是"子进程明明跑成功了, 但父进程说失败", 而且报错里出现 `Exception in thread Thread-1 (_readerthread)`, 见到这个栈就查这里
- 同理, 读子进程写出的文本文件时也要显式 `encoding="utf-8"`

## 三, 渲染层 (最容易翻车, 也最难自查)

画面上的每一个字都要由某个字体的某个字形来画, 字体没有这个字形时 Pillow 会画一个空心方框, 而且**不报错**.

### 会出问题的字符类型

| 类型 | 例子 | 风险 |
|:---:|:---|:---|
| 上标下标 | ₂ ₃ ⁸ ¹³ ¹⁸ | 中文字体常常只有一部分, 缺的会变豆腐块 |
| 数学符号 | ≈ ≤ ≥ × ÷ ∑ ∫ √ ∞ | 中文字体覆盖不全 |
| 希腊字母 | θ λ β α Δ | 一般都有, 但仍需体检 |
| 箭头与勾叉 | → ← ↑ ↓ ✓ ✗ | 中文字体与等宽字体覆盖不一致 |
| 生僻字与异体字 | 硤 硖 卡甘 | 简繁差异, 人名地名最常见 |
| 全角与半角混排 | `（` `）` `:` `;` | 不报错但版式会歪, 见 `conventions.md` 的文档规范 |

### 同一个字符在不同字体里可能一个有, 一个没有

本技能实测: `₂` (U+2082) 在中文字体 msyhbd 里**缺字形**, 在等宽字体 Consolas 里**有字形**. 所以同一句混排文本, 换个字体键就可能从豆腐块变成正常.

结论: 字形体检必须按字体逐个做, 不能只测一个字体就认为安全.

### 体检方式: 位图精确比对

不要用字宽判断. 上标下标这类窄字符的字宽与豆腐块很接近, 用宽度阈值会大量误报 (实测 `⁸` 就被误判过).

正确做法是把待测字符与私用区字符 `\ue000` 分别渲染成位图, 逐像素比对, 完全相同才是豆腐块. `scripts/check_text.py` 已实现:

```
python scripts/check_text.py
python scripts/check_text.py --font cnb "iPr₂Zn" "¹³C / ¹⁸O" "≈¥0.05"
python scripts/check_text.py --font mono "iPr₂Zn"
```

实测输出:

```
[bad]  cnb    缺字形 1 个: ₂(U+2082)
[ok]   mono   共 20 个字符全部有字形
```

### 缺字形的三种处理

1. 换 ASCII 写法, 最稳. `iPr₂Zn` 写成 `iPr2Zn`, `¹⁸O` 写成 `18O`
2. 换字体键. 中文缺的字符常常等宽字体有, 用 `kind="mono"` 单独画这一段
3. 换成别的表达. 上标下标改写成 `^` 与 `_` 的普通写法

### 逐字自动回退 (引擎内建, 默认开启)

上面那三种处理都要人去改代码, 漏改一处就是一处静默的豆腐块. 所以画面引擎把第一种和第二种做法做成了自动行为: `canvas.py` 的 `text()` 会**逐字**检查当前字体键有没有该字符的字形, 没有就沿回退链换一个字体键, 同一句文本里换键的地方自动分段渲染.

回退链写在 `canvas.py` 的 `FALLBACK`:

| 原字体键 | 依次回退到 | 动机 |
|:---:|:---|:---|
| `mono` | `cnb`, `cn` | 等宽字体没有中文字形, 中文必须回退到中文字体 |
| `monor` | `cn`, `cnb` | 同上 |
| `cnb` | `monor`, `mono` | 中文粗体常常缺上下标与数学符号, 等宽字体反而有 |
| `cn` | `monor`, `mono` | 同上 |

三个必须知道的细节:

- **判定方式与体检一致**, 都是位图精确比对私用区字符 `\ue000`, 不用字宽. 结果按 (字体键, 字符) 缓存, 所以逐字检查不会拖慢渲染
- **`measure()` 也按回退后的实际宽度累加**, 于是量出来的宽度与真正画出来的宽度一致, 混排布局不会错位; 中英混排仍然可以照旧用 `rich()`, 它会自动享受回退
- **无需回退时走 Pillow 原生路径**, 渲染结果与回退功能加入之前逐像素相同, 所以历史成片不会被这次改动影响; 已用同一场景的帧哈希对照验证
- 想自查某句话会被怎么拆, 用 `c.text_runs(s, kind)`, 它返回 `((片段, 字体键), ...)`

回退不是万能的: 回退链上**所有**字体都缺该字形时, 它仍然会画成豆腐块. 这一类必须靠下面的渲染期审计抓出来.

### 与混排的配合

中英混排时中文用 `cnb`, ASCII 用 `mono`, 逐段测量宽度再累加 (见 `visual-engine.md` 的 `rich`). 这样既能保证中文字形, 又能保证数字与符号的字形, 顺带得到等宽数字不跳动的好处.

有了逐字回退之后, 混排的容错变好了, 但**不要因此把字体键写随意**: 整句中文用 `mono` 虽然会被回退救回来, 却会让整句都走分段渲染, 而且审计报告里会多出一堆本可避免的条目. 仍然按语义选键: 中文用 `cnb` 或 `cn`, 数字与符号用 `mono` 或 `monor`.

### 渲染期审计 (引擎内建, 渲染时自动开)

体检工具 `check_text.py` 只检查你**主动喂给它**的字符串, 静态扫源码还会漏掉拼接出来的文本, 也会把从不执行的分支算进来. 唯一可靠的证据是**真正被画出来的东西**, 所以引擎在渲染时自动收集:

- `render_range()` 渲染时自动开启审计, 区间渲完打印一份报告; 分区间并行时每个进程各报自己那一段, 合起来覆盖全片
- 审计劫持 `text()`, 记录去重后的 (字符串, 字体键) 组合, 以及每个组合里哪些字符发生了回退, 回退到了哪个键
- 报告分三档: **无回退**(全部用原字体键), **发生回退**(列出字符与去向, 附出现该组合的原始字符串), **回退链也找不到字形**(这些会画成豆腐块, 必须人工处理)

报告长这样:

```
渲染期字形审计 帧区间 [0, 3240)
  text() 调用 41230 次, 去重后 68 个 (字符串, 字体键) 组合
  发生回退 4 个组合:
    [mono] 产(U+4EA7)->cnb 物(U+7269)->cnb
        出现该组合的字符串: '产物 ee'
    [cnb] ₂(U+2082)->monor
        出现该组合的字符串: 'iPr₂Zn'
  警告: 1 个组合里有回退链也找不到字形的字符, 这些会画成豆腐块:
    [cnb] 😀(U+1F600)   字符串 '😀'
  处置: 改成 ASCII 写法, 或换一个确实有该字形的字体键, 见 references/text-and-encoding.md
```

三条使用纪律:

1. **必须覆盖全片**. 只在开头抽几十秒扫, 会漏掉后半段才出现的组合. 实测有 9 处"中文误用等宽字体"分散在四个坐标轴标签, 两个图例, 标题卡日期行与片尾两行, 只扫前 30 秒漏了 8 处
2. **"发生回退"不是错误, 是提示**. 回退本身把豆腐块救回来了, 但每一条都值得回头看: 如果整句中文都从 `mono` 回退到 `cnb`, 说明这个字体键选错了, 直接把它改对更干净
3. **"回退链也找不到字形"必须处理**, 它是交付前的阻断项. 改 ASCII 写法, 或换一个确实有该字形的字体键

### 自备字体的两条纪律

需要引入系统之外的字体时:

- **子集化拉取中文字形**: CJK 整包字体动辄十几 MB, 而 Google Fonts 的 CSS API 支持 `&text=` 参数只返回用到的字形: 向 `https://fonts.googleapis.com/css2?family=Noto+Sans+SC:wght@700&text=<URL编码的上屏字符全集>` 请求, 下载它指向的字体文件放进工程 `fonts/` 目录. 这样既解决许可 (OFL), 又把体积压到几十 KB. 上屏字符集变化后要重新拉一次.
- **渲染时不得在线链接字体**: 不要在任何渲染路径里写远程字体 URL; 渲染必须只依赖本地文件, 否则离线环境直接失败, 而且同一份工程换个网络环境渲出来的字形可能不同. 字体一律先落到工程目录再加载.

## 四, 交付前必做的三步

1. 把所有会出现在画面上的字符串集中成一张常量表, 便于一次性体检与替换
2. 对每个用到的字体键跑一次 `check_text.py` 做**渲染前**体检
3. 全片渲染后读**渲染期审计报告**, 把"回退链也找不到字形"的项全部处理掉, 再抽帧做字符图预览 (豆腐块在字符图里表现为一个孤立的方形亮块, 能看出来)

## 五, 本次会话的真实案例

| 现象 | 层 | 处理 |
|:---|:---:|:---|
| 用 PowerShell 切片源码后中文变成 `鍧愭爣绯` | 文件层 | 改用 Python 读写, 重做切片 |
| `print` 片尾成本字符串抛 `UnicodeEncodeError` | 控制台层 | 源码里写成 `"\u00a5"`, 并设 `PYTHONIOENCODING` |
| 人名用字 `硤` 与 `硖` 不确定字形是否存在 | 渲染层 | 位图比对确认两个字都有字形, 按简体规范选用 `硖` |
| 反应式里的 `iPr₂Zn` 用了中文粗体, `₂` 缺字形 | 渲染层 | 查出后改为 `iPr2Zn`, 或该段改用等宽字体 |
| 四个坐标轴标签, 两个图例, 标题卡日期行与片尾两行都用 `mono` 画了中文 | 渲染层 | 只做渲染前体检挡不住这类静默复发, 加逐字回退后自动救回; 渲染期审计把 9 处全部列了出来 |
