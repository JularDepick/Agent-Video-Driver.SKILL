# 单帧成本实测口径

本文回答一个问题: 一帧的时间花在哪, 以及怎么在同一台机器上把它量出来.

- 画面引擎的性能信息原本只散在 `visual-engine.md` 的几条量级描述与 `resources.py` 的限额常量里; 本文补的是"单帧耗时按部件拆开"的实测口径, 配套探针是 `scripts/perf_probe.py`
- 本文里的每个数字都是在本机跑那个探针跑出来的, 测量条件写在第一节; 换机器必须重测, 耗时不带机器信息就没有意义
- `scripts/resources.py` 现在只按帧数估磁盘与内存, 不估耗时; 本文给的是在本机复测耗时的方法与一次实测基线, 它没有改动 `resources.py`, 也不给它加耗时常量

## 一. 测量机器与条件

| 项 | 值 |
|:---:|:---:|
| CPU | Intel(R) Core(TM) i7-14650HX |
| 逻辑核数 | 24 |
| 物理内存 | 15.71 GB |
| 测量开始时可用内存 | 4.20 GB |
| 测量开始时内存负载 | 73% |
| 测量结束时可用内存 | 4.29 GB |
| 测量结束时内存负载 | 72% |
| 操作系统 | Windows |
| Python | 3.13.7 |
| numpy | 2.2.6 |
| Pillow | 12.3.0 |
| 命令 | `python skills/agent-video-driver/scripts/perf_probe.py --repeat 9` |
| 画幅 | 设计 1920 x 1080 px, 超采样 SS=2, 画布网格 3840 x 2160 |
| 帧内容 | 51 个矢量图元 + 6 次文字调用 + 一个点云 (96 x 48 点, splat=2, soften=2) + 一次 PNG 落盘 |
| 计时口径 | 同一张表内各项同轮交替计时, 每项预热 1 次, 表一表二 9 轮, 表三表四 2 轮, 每项取各轮最小值 |
| 该次测量的内存带宽参照 | 全网格单轴前缀和 90.64 ms |
| 该次探针自身耗时 | 82 秒 |

三点说明:

- 测量期间本机还有别的进程在跑, 所以这是一次带外部争用的读数, 不是这台机器的最快成绩; 同一条命令在同一台机器上四次运行里量到的整帧最小值在 274.19 到 1220.26 ms 之间, 见第十节
- 内存带宽参照行是每张表都带的一行"全网格单轴前缀和", 它只做内存读写; 两张表要比较时先比这一行, 它差得多说明两张表跑在轻重不同的负载下
- 探针量的是它自己那份图元清单, 不是任何真实分镜. 真实分镜的单帧成本要用自己的场景模块单独量, 本文不代替那件事

## 二. 四段口径

| 段 | 一帧里包含什么 | 依据 |
|:---:|:---:|:---:|
| A | Pillow 矢量与文字: 直线, 实心圆, 圆角矩形, 多边形, 虚线, 圆弧, 发光线与发光圆, 以及 `text` `text_fit` `text_cap` `rich` `measure` 驱动的文字 | `canvas.py` 的 `C` |
| B | numpy 后期: 覆盖率包围盒内的箱式模糊 (sigma=1.2) 与全网格 `min_filter` (r=1) | `imgnp.py` 的 `blur` `min_filter` |
| C | 3D 点云: 曲面采样, 点云渲染, 与画布合成 | `three.py` 的 `sample` `render`, `canvas.C.cloud` |
| D | 帧写盘: `img.save(compress_level=3)`, 与 `canvas.render_range` 同一个调用 | `canvas.py` 的 `render_range` |
| 帧组装 | 画布初始化 (背景拷贝) 与 `reduce(SS)` 降采样 | `canvas.py` 的 `C` 与 `render_frame` |

占比的分母一律是整帧实测值. 有两类算子**不进** B 段的每帧口径, 它们的读数单列在第五节:

- 大半径 FFT 模糊属于纸底这类一次性产物 (`print-engine.md` 的逐帧管线一节写明"纸底与油墨覆盖率只生成一次")
- 亚像素平移 `shift2` 只在套印偏移那一拍为非零, 平时 `misreg` 给 0

## 三. 实测分布

| 段 | 一帧工作量 | min ms | mean ms | 轮数 | 占整帧 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 内存带宽参照 | 全网格 2160 x 3840 | 90.64 | 107.77 | 9 | - |
| A Pillow 矢量与文字 | 51 图元 + 6 文字 | 126.38 | 138.15 | 9 | 10.5% |
| B numpy 后期 | 包围盒箱式模糊 + 全网格 min_filter | 284.89 | 303.14 | 9 | 23.8% |
| C 3D 点云 | 采样 + 渲染 + 合成 | 518.83 | 539.42 | 9 | 43.3% |
| D 帧写盘 | PNG 1 张 | 169.95 | 190.93 | 9 | 14.2% |
| 帧组装 | 画布初始化 28.24 + 降采样 27.08 | 55.33 | 60.45 | 9 | 4.6% |
| 整帧 | 四段 + 帧组装串一遍 | 1198.23 | 1252.35 | 9 | 100.0% |

三条读数:

- 最贵的是 3D 点云通道 (43.3%), 其次是 numpy 后期 (23.8%), 第三是帧写盘 (14.2%); Pillow 的矢量与文字整段只占 10.5%
- mean 明显大于 min 的行说明那一行的各轮受了外部争用, 引用时以 min 为准, mean 用来看干扰有多大
- 四段加帧组装合计 96.4%, 差额 +3.6% 见第七节

## 五. 一次性的与只在部分帧上跑的算子

| 算子 | min ms | mean ms | 轮数 | 占整帧 |
|:---:|:---:|:---:|:---:|:---:|
| [变体] 亚像素平移 shift2, 全网格 | 1047.53 | 1125.64 | 2 | 87.4% |
| [变体] FFT 模糊 sigma=9.0, 全网格 | 2531.05 | 2687.92 | 2 | 211.2% |
| 内存带宽参照 | 107.92 | 111.82 | 2 | - |

**这就是"算子快 N 倍不等于整帧快 N 倍"的实测出处**: FFT 模糊那一行是整帧的 211.2%, 但它属于一次性纸底, 不在逐帧链上; 把它的算子耗时降下去, 逐帧耗时一点都不会变. 套印平移同理, 它只在偏移那一拍跑, 87.4% 这个比例只对那一拍成立.

## 六. 逐算子对照

画布网格 2160 x 3840, float32 单通道, 同一轮内取最小值.

| 类 | 条件 | min ms | mean ms | 轮数 |
|:---:|:---:|:---:|:---:|:---:|
| 基准 | 前缀和单轴, 全网格 (内存带宽参照) | 105.89 | 108.33 | 2 |
| 模糊 | 箱式 sigma=1.0 (r=1), 全网格 | 1098.05 | 1115.46 | 2 |
| 模糊 | 箱式 sigma=2.0 (r=2), 全网格 | 1172.14 | 1199.08 | 2 |
| 模糊 | 前缀和箱式 box_blur r=9, 全网格 | 1135.58 | 1148.79 | 2 |
| 模糊 | 覆盖率包围盒 633 x 606 内 sigma=1.2 | 23.34 | 27.66 | 2 |
| 邻域 | min_filter r=1, 全网格 | 266.22 | 270.31 | 2 |
| 邻域 | min_filter r=2, 全网格 | 510.30 | 540.69 | 2 |
| 邻域 | max_filter r=1, 全网格 | 256.28 | 285.61 | 2 |
| 平移 | shift2 单通道, 全网格 | 1146.30 | 1150.43 | 2 |
| 平移 | shift2 三通道, 全网格 | 2766.77 | 2776.20 | 2 |
| 写盘 | img.save compress_level=3 | 127.59 | 162.74 | 2 |
| 写盘 | img.save compress_level=6 | 153.21 | 192.73 | 2 |

五条读数:

- 半径从 1 提到 9, 箱式路径只从 1098.05 涨到 1135.58 ms (+3.4%): 它的成本几乎全在填充边界的复制与前后缀和, 与窗口宽度关系很小
- 同一半径 9 上, 前缀和箱式 1135.58 ms 对 FFT 2531.05 ms (第五节的变体行), 箱式便宜 2.2 倍. `imgnp.blur` 现在的分界是 sigma 小于 3 走箱式, 实测在这个网格上箱式的优势一直延伸到 r=9
- 邻域滤波的成本与半径近似线性: r=1 是 266.22 ms, r=2 是 510.30 ms, 因为 r=2 要做的错位比较次数是 r=1 的两倍
- 同样走箱式且同为 r=1 的两次调用: 全网格 1098.05 ms, 覆盖率包围盒 (633 x 606, 占全网格 4.6%) 内 23.34 ms, 相差 47 倍. 全画幅算子的第一手段就是收进包围盒
- 写盘的 3 档与 6 档在另外几次运行里高低并不一致 (有一次 3 档更贵), 所以不要用这张表选压缩档; 这两行只说明落盘本身是百毫秒量级

## 七. 整帧与四段之和的差别

| 项 | 值 |
|:---:|:---:|
| 整帧实测 (预热后) | 1198.23 ms (min of 9, 均值 1252.35 ms) |
| 冷首帧 (任何预热之前) | 1714.35 ms |
| 四段之和 A+B+C+D | 1100.04 ms (占整帧 91.8%) |
| 帧组装 | 55.33 ms (占整帧 4.6%) |
| 差额 = 整帧 - 四段之和 - 帧组装 | +42.86 ms (占整帧 +3.6%) |
| 落盘 PNG 体积 | 0.301 MB |

- 差额来自整帧里各段缓冲的分配与访问次序: 四段单独计时时, 各项的缓冲在各轮之间被反复复用, 而整帧每帧都要新建画布与各段缓冲. 差额只有 3.6%, 说明四段加帧组装基本覆盖了整帧, 没有大块没计入的工作
- 冷首帧比稳态贵 516.12 ms (+43.1%), 这一份是背景预渲染, 字体加载与字形位图缓存的一次性成本; 它只在第一帧上付
- 探针没有把差额继续往下拆, 也没有把 FFmpeg 编码算进来: 编码在帧序列之外, 不属于"单帧成本"

## 八. 判据: 什么值得优化, 什么不值得

判据三条:

- 先确认这一行**在不在逐帧口径里**. 一次性纸底的大半径 FFT 模糊是整帧的 211.2%, 但它不在逐帧链上; 套印平移是整帧的 87.4%, 但它只在偏移那一拍跑. 对这两类算子做算子级优化, 逐帧耗时不会有任何变化
- 只优化占整帧比例大的行, 且**收益上限就是那一行的占比**: 某行占整帧 X%, 无论它快多少倍, 整帧的收益也到不了 X% 以上
- 全画幅算子的第一手段是收进包围盒, 实测同一算子差 47 倍 (23.34 对 1098.05)

按这个判据, 本机这次实测值得动的三项:

| 项 | 实测 | 占整帧 | 为什么 |
|:---:|:---:|:---:|:---:|
| `canvas.C.cloud` 的全网格 alpha 与 fog 乘算 | 313.49 ms | 26.2% | 同一帧里包围盒只占全网格 4.6% 的像素, 而这一项是整帧最贵的单项; 按包围盒裁一次是全画幅算子上已验证的手段 |
| `min_filter` r=1 全网格 (内侧剪影线) | 260.00 ms | 21.7% | 每帧在全网格上做一次; 覆盖率包围盒只有 633 x 606, 收进包围盒或降一档网格再做 |
| PNG 落盘 | 169.95 ms | 14.2% | 单项就占 14.2%, 比整个 Pillow 绘制段还大; 但压缩档的取舍在这台机器上量不出稳定结论, 不要凭这张表调档 |

不值得动的三项:

| 项 | 实测 | 为什么 |
|:---:|:---:|:---:|
| 把 Pillow 矢量与文字整段换掉 | 126.38 ms | 整段占 10.5%, 这是收益上限; 段内已量出大头是圆角矩形与文字, 先减数量或改画法 |
| 一次性纸底的大半径 FFT 模糊 | 2531.05 ms | 不在逐帧链上, 对逐帧耗时没有影响 |
| 换硬件或重写 3D 光栅化 | 518.83 ms | 3D 整段占 43.3%, 但探针量的是"每帧都有一个投影半径占画幅高度 16% 的点云"; 真实分镜里不是每帧都有 3D, 用整片平均去看它才会得出不同的结论 |

## 九. 怎么复测

```bash
python skills/agent-video-driver/scripts/perf_probe.py
python skills/agent-video-driver/scripts/perf_probe.py --repeat 9 --size 1920x1080
python skills/agent-video-driver/scripts/perf_probe.py --repeat 3 --size 960x540 --out temp/perf_probe
```

- `--repeat N` 是表一表二的计时轮数, 缺省 9; 表三表四里有几秒级的算子, 固定压到 2 轮
- `--size WxH` 是设计画幅, 缺省 1920x1080; 超采样倍数沿用 `canvas.py` 的 `SS=2`, 画布网格是设计画幅的两倍
- `--out DIR` 是帧写盘段的落盘目录, 缺省 `temp/perf_probe`; 探针只在它下面覆盖写一张 `frame_<W>x<H>.png`, 不写别的路径
- 三个参数都有 `--help` 说明
- 探针不依赖工程目录之外的东西: 它只 import 同目录的 `canvas.py` `imgnp.py` `three.py` 与标准库; 文字那几行需要 `canvas.py` 的 `FONT_PATH` 指向的字体存在, 缺字体时文字行会报错而不是静默给个假数
- 一次完整运行 (`--size 1920x1080 --repeat 9`) 在本机实测耗时 78, 82, 93 秒 (三次运行)
- 复测时机器上别的同时在跑的重活会把结果抬高数倍, 这是本机实测到的事实 (见第十节); 探针每张表都带内存带宽参照行, 就是给这件事用的

## 十. 怎么读结果

- 看表头: CPU 型号, 逻辑核数, 内存与测量前后的负载. 没有这些, 后面的毫秒数没有意义
- 看表一那一行的内存带宽参照: 它是这张表跑在多重负载下的标尺
- 看表一的四段占比: 这是本文的主结果, 也是唯一可以跨机器比的部分
- 看表二的段内明细: 明细与段级在同一轮里测出, 两者相差几个百分点以内说明明细拆得对
- 看第五节的两个变体行: 它们提醒你哪些大数字不在逐帧链上
- 看第七节的差额: 差额小说明四段口径覆盖完整; 差额大就去查是不是有别的段没被拆出来

| 3 | 90.64 | 1198.23 | 10.5% | 23.8% | 43.3% | 14.2% | 4.6% |
| 4 | 62.83 | 1220.26 | 7.9% | 22.3% | 43.4% | 9.4% | 4.3% |

- 绝对毫秒数在四次运行里差了 4.4 倍 (274.19 到 1220.26 ms), 内存带宽参照也跟着差了 4.4 倍 (20.73 到 90.64 ms); 这台机器当时的负载就是这么大
- 四段占比基本稳定: C 在 43.3% 到 46.0%, B 在 22.3% 到 26.2%, A 在 7.9% 到 10.5%, D 在 9.4% 到 14.2%, 帧组装在 4.3% 到 5.3%
- 结论: **占比可以引用, 绝对毫秒数必须连测量条件一起引用**. 同一台机器上换一个负载窗口就能差数倍, 换机器更不用说

## 十一. 本文实测到的结论

- 一帧里最贵的两项是 `canvas.C.cloud` 的全网格合成 (占整帧 26.2%) 与 `min_filter` r=1 全网格 (21.7%), 两项合计 47.9%
- Pillow 的矢量与文字整段占 10.5%, 段内大头是 6 个圆角矩形 (58.4%) 与 6 次文字调用 (27.2%)
- PNG 落盘单项占 14.2%, 比整个 Pillow 绘制段还贵
- 帧组装 (画布初始化 + 降采样) 占 4.6%; 四段加帧组装 96.4%, 与整帧的差额 +3.6%
- 冷首帧 1714.35 ms 比稳态 1198.23 ms 贵 43.1%, 差的是背景预渲染与字体加载
- 一次性纸底的大半径 FFT 模糊是整帧的 211.2%, 套印平移是整帧的 87.4%, 两者都不在逐帧链上: 算子级的倍数不能拿来推断整帧
- 同一算子从全网格收进覆盖率包围盒, 实测从 1098.05 ms 降到 23.34 ms (47 倍)
- 同半径下前缀和箱式模糊比 FFT 便宜 2.2 倍 (1135.58 对 2531.05 ms), 且半径从 1 提到 9 只贵 3.4%
- 本机负载能把整帧从 274.19 ms 抬到 1220.26 ms, 而四段占比几乎不变
- `scripts/resources.py` 仍只按帧数估磁盘与内存, 不估耗时; 本文没有改动它, 本文的数字也不能当作它的常量

> 本文所有数字来自同一台机器 (Intel(R) Core(TM) i7-14650HX, 24 逻辑核, 15.71 GB 内存, Windows, Python 3.13.7, numpy 2.2.6, Pillow 12.3.0), 命令与轮次见第一节与第九节; 换机器必须重测
