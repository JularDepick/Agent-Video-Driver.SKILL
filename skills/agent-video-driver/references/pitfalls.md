## 一, 沙箱与进程

**1. multiprocessing 直接报 WinError 5**
现象: `PermissionError: [WinError 5] 拒绝访问` 出现在 `mp.Pool` 创建时, 栈底是 `_winapi.CreateFile` 与 `connection.Pipe`.
原因: Windows 上 multiprocessing 的队列与管道走命名管道, DSH 沙箱在受限模式下禁止打开命名管道.
规避: 不要用 `mp.Pool`. 要并行就按帧区间开 N 个独立进程, 每个进程只写自己那段帧文件, 进程间零通信. 渲染脚本设计成接收 `<start> <end>` 参数正是为此.

**2. Start-Process 起的子进程会连带被杀**
现象: 一条 pwsh 里用 `Start-Process` 起 4 个 python, 父进程 `Wait-Process` 报 `Access is denied`, 随后 4 个 python 全部消失, 帧数为 0.
原因: 父作业结束时把子进程一起收走了, 且沙箱不允许对子进程句柄等待.
规避: 用工具自身的后台作业机制, 一个区间一个作业, 不要自己造进程组.

**3. Node 侧 spawn 抓不到子进程输出**
现象: 文档中记载的边界, Node 的 `child_process.spawn` 默认 `stdio: 'pipe'` 会 EPERM.
规避: 用 `stdio: 'inherit'` 或让程序自己写文件.

## 二, 坐标与调度 (最致命的两类)

**4. 单位坐标与像素坐标混用**
现象: 数学场景整场戏挤到画面左上角, 坐标轴只剩 28px 长.
原因: 画布方法吃的是设计 px, 而场景里传的是数学单位 (3, 2), 变换函数当时写成了 `OX + (x - OX) * z`, 把单位当像素算.
规避: 显式定义 `G(x, y)` 做单位到像素映射, 所有数学图形调用处一律写 `c.arrow(G(0,0), G(3,2), ...)`. 画完先用字符图确认原点落在画面中心.

**5. 段落调度 off-by-one**
现象: 每段内容整体错位一段, 第一段 (0 到 7.2s) 完全空白, 最后一段内容被截断.
原因: 区间 `[SEG[j], SEG[j+1])` 映射到了 `SCENES[j]`, 而首段其实在 `[0, SEG[0])`.
规避: 调度写成显式两分支, 并在渲染前打印每段的起止帧核对:

```python
k = 0
if t >= SEG[0]:
    k = len(SCENES) - 1
    for j in range(len(SEG) - 1):
        if SEG[j] <= t < SEG[j+1]:
            k = j + 1
            break
```

**6. 浮点累加漂移**
现象: 长片后半段卡点逐渐偏移几帧.
原因: 用 `t += BEAT` 累加 180 次.
规避: 一律 `k * BEAT` 一次算出.

## 三, 渲染与体积

**7. PNG 单帧 1.9MB**
现象: 900 帧占 1.7GB, 写盘比渲染还慢.
原因: 背景里加了逐像素随机噪声, PNG 无法压缩.
规避: 帧里不加噪点, 颗粒交给 FFmpeg 的 `noise=alls=2:allf=t`. 同样内容单帧降到 200KB.

**8. 颗粒与 CRF 的体积陷阱**
现象: 同一批帧, CRF16 加 `alls=3` 出 204MB, CRF19 加 `alls=2` 只出 8.9MB.
原因: 时间颗粒是编码器最难压的东西, 降低颗粒幅度并放宽 CRF 后编码器直接把它平滑掉了.
判据: 不要只看体积, 用 PSNR 判定. 本例 8.9MB 版本的 PSNR 是 53.7dB, 属于视觉无损, 体积差异全部来自颗粒.
规避: 先定颗粒强度再定 CRF, 交付前必须量 PSNR.

**9. 发光用高斯模糊会拖垮渲染**
现象: 单帧 0.4 秒以上.
原因: 4K 中间画布上做 `GaussianBlur` 每帧几十到几百毫秒.
规避: 用三层宽低透明度描边模拟发光, 只在小区域用 `bloom` 做 screen 混合.

## 四, 音频

**10. 高频刺耳**
现象: 用户反馈 BGM 刺耳, 频谱检查发现 2 到 6kHz 占 36.8%, 谱心 2193Hz, 温暖区只有 0.6%.
原因: 打击乐全部用白噪声 (镲, 沙锤, 拍手), 混响 IR 没低通, 母带还加了高频架提升.
规避: 打击乐改用低通噪声加音体, 混响 IR 低通到 2.4kHz, 总线加高频衰减, 补 220 到 900Hz 温暖区. 目标谱心 600 到 1500Hz.

**11. 低频浑浊**
现象: 20 到 90Hz 占比 69.9%, 小喇叭上完全听不到旋律.
原因: 低音写在根音下方八度 (C2 约 65Hz) 且电平 0.85.
规避: 低音写在 C3 附近, 电平降到 0.4, 加 32Hz 高通.

**12. 电平忽大忽小**
现象: 电平图上一格满一格空.
原因: 没有总线压缩.
规避: 用 0.09s 包络做软压缩, 阈值 0.16, 超出部分 0.55 次幂.

**13. 卡点验证不能靠耳朵**
规避: 逐帧差分找运动峰值, 核对是否落在小节线正负 1 帧内, 方法见 `beat-sync.md`.

## 五, 文本与编码

文本要过三层, 病因与治法完全不同, 详细方法与案例见 `text-and-encoding.md`. 这里只列现象:

**14. 控制台 GBK 打印报错**
现象: `UnicodeEncodeError: 'gbk' codec can't encode character '\xa5'`.
规避: 脚本里避免直接打印非 GBK 字符 (用 `\u00a5` 转义), 或先设 `PYTHONIOENCODING=utf-8`.

**15. PowerShell 读写中文文件乱码**
现象: 用 `Get-Content` 读 UTF-8 的 py 再 `Set-Content` 写出, 中文变成 `鍧愭爣绯`.
原因: 读取时按 ANSI 解码.
规避: 文本切片与改写一律用 Python 处理, 显式 `encoding='utf-8'` 与 `newline='\n'`.

**16. 画面上的字静默变成豆腐块**
现象: 反应式里的 `iPr₂Zn` 显示成 `iPr□Zn`, Pillow 不报任何错.
原因: 中文粗体 msyhbd 没有 `₂` (U+2082) 的字形, 而同一个字符在 Consolas 里是有的.
规避: 渲染前对每个字体键跑 `scripts/check_text.py` 做位图比对, 缺字形就改成 ASCII 写法或换字体键.
注意: 不要用字宽做判据, 上标下标这类窄字符的字宽与豆腐块接近, 会误报 (实测 `⁸` 被误判过).

**17. 字体缺字判断**
规避: 渲染待测字符与私用区字符 `\ue000` 各一张位图, 逐像素比对, 完全相同才是豆腐块.

## 六, 配乐 (刺耳与单调)

**18. 高频刺耳**
现象: 用户反馈 BGM 刺耳, 频谱检查发现 2 到 6kHz 占 36.8%, 谱心 2193Hz, 温暖区只有 0.6%.
原因: 打击乐全部用白噪声 (镲, 沙锤, 拍手), 混响 IR 没低通, 母带还加了高频架提升.
规避: 打击乐改用低通噪声加音体, 混响 IR 低通到 2.4kHz, 总线加高频衰减, 补 220 到 900Hz 温暖区.

**19. 低频浑浊**
现象: 20 到 90Hz 占比 69.9%, 小喇叭上完全听不到旋律.
原因: 低音写在根音下方八度 (C2 约 65Hz) 且电平 0.85.
规避: 低音写在 C3 附近, 电平降到 0.4, 加 32Hz 高通. 管弦乐拨弦写在 110 到 220Hz.

**20. 电平忽大忽小**
现象: 电平图上一格满一格空.
原因: 没有总线压缩.
规避: 用 0.09 到 0.10 秒包络做软压缩. 但注意下一条.

**21. 压缩器把拍点压平 (最隐蔽的一条)**
现象: 配乐听不出拍, 折叠包络几乎水平, 拍上/拍间能量比 0.99.
原因: 总线压缩的时间常数 0.10 秒, 与打击瞬态长度相当, 压缩器正好跟住每个鼓点把它压回去.
规避: 需要脉冲的音乐, 压缩时间常数取 0.3 到 0.5 秒, 阈值放宽到 0.22 左右. 改后比值恢复到 1.29.

**22. 持续声部变成声墙, 掩掉拍点**
现象: 对位声部每小节奏长音时, 该总线 RMS 0.166, 节奏层只有 0.045, 折叠包络起伏仅 0.10.
原因: 任何时长不小于小节且每小节都出现的声部都会连成一片, 把瞬态盖住.
规避: 持续层总 RMS 必须低于节奏层, 对位声部改成隔小节出现且时值压到 2 拍以内.

**23. 长衰减拨弦糊掉琶音**
现象: 竖琴衰减 1.8 秒时八分音符琶音叠成连续声, 拍点消失.
规避: 装饰性拨弦衰减压到 1 秒以内, 拍上与拍间拉开电平差 (实测 0.20 对 0.06).

**24. 全片一套配置跑到底 (单调)**
现象: 每 10 秒 RMS 起伏只有 1.30 倍, 听感平.
规避: 十段式配器表, 每段换乐器组合与音区, 旋律用动机加变奏, 加力度弧线. 改后起伏 2.80 倍.

## 七, 工具与环境

**25. 命令行参数解析松散导致白跑一遍**
现象: 想渲染 780 帧, 实际渲染了 900 帧 (含尚未定稿的片头).
原因: `mode = sys.argv[1]`, 而实际传的是 `render main`, 取到 `render` 后落进了 else 分支.
规避: 参数解析写显式映射, 并在启动日志里打印"将渲染 [a, b) 共 N 帧".

**26. 子进程输出被吞或进程被连带杀死**
现象: 自建进程组时子进程随父进程一起消失, 帧数为 0.
原因: 沙箱不允许对子进程句柄等待, 父作业结束会收走子进程.
规避: 用工具自带的后台作业机制, 一个帧区间一个作业.

## 八, 协作与预期

**27. 一次会话只做一条片**
原因: 长会话的缓存命中会累计到千万级 token, 上下文里堆满上一条片的细节, 后续每一步都变慢变贵.
规避: 第二条片另开会话, 技能本体与脚本可跨会话复用.

**28. 无视觉能力却按想象交付**
规避: 每个段落抽帧做字符图核对, 并用 PSNR, 响度, 运动能量三类客观指标兜底, 交付时明确告知用户"观感需要你过目".

**29. 不先问代价就开渲染**
规避: 启动确认门, 见 SKILL.md 第一节.

## 九, 渲染路线与工具链 (本轮新增)

**30. 浏览器在受限沙箱里根本起不来**
现象: 直接调 chromium 加 `--headless=new --screenshot=...`, 立刻 FATAL, 报 `mojo\public\cpp\platform\platform_channel.cc: Check failed: . : 拒绝访问 (0x5)`, 截图文件不生成. 加上 `--single-process --no-zygote` 也一样, 只多出一行 `Cannot use V8 Proxy resolver in single process mode`.
原因: Chromium 内部进程间通信用命名管道 (mojo channel), 受限沙箱禁止打开命名管道, 与 `multiprocessing` 报 WinError 5 是同一个根因.
规避: 不要把画面路线建立在浏览器上. 默认路线是 Python + Pillow 逐帧渲染, 它只用文件系统, 不受这条限制. 若确实需要浏览器渲染, 必须在沙箱外执行, 并提前告诉用户这一步需要放宽权限.

**31. Python 的 Playwright 驱动同样被命名管道拦住**
现象: `sync_playwright().__enter__()` 抛 `PermissionError: [WinError 5] 拒绝访问`, 栈底落在 `asyncio\windows_utils.pipe` 的 `_winapi.CreateFile`.
原因: Playwright 的 Python 绑定用 asyncio 子进程加管道与 node 驱动通信, 走的是命名管道. 注意这与 `subprocess.run(..., capture_output=True)` 不同, 后者实测可用, 因为它是匿名管道.
规避: 探测环境时如实报告"浏览器不可启动"并走 Python 路线, 不要反复尝试别的启动参数.

**32. 抽帧用 `-ss` 前置会取到近似帧, 卡点判据就失效了**
现象: 要做"切点前后各一帧"的对比, 结果两张图差异很小, 看起来卡点没对上.
原因: `ffmpeg -ss <t> -i <视频>` 是输入定位 (快速定位), 它跳到目标时间之前最近的关键帧再解码, 关键帧稀疏时取到的不是目标帧.
规避: 精确定位要把 `-ss` 放在 `-i` 之后 (`ffmpeg -i <视频> -ss <t> -frames:v 1 ...`). 判据精度要求到帧时, 必须用后者. `scripts/qa.py` 已按精确定位实现.

**32.1 输出侧定位的请求时间会因进位越过目标帧**
现象: 已经改用输出侧定位, 抽第 44 帧却拿到第 45 帧, 卡点验收整体偏一帧.
原因: 第 44 帧的时间戳是 `44/30 = 1.46666...`, 请求时间写成 `%.4f` 会进位成 `1.4667`, 已经大于目标帧的时间戳, 而输出侧丢的是时间戳小于请求时刻的帧, 于是给的是下一帧.
规避: 请求时间往前挪半帧 (即 `t - 0.5/fps`) 再用, 并把格式化精度提到 `%.6f`. 前挪半帧既不会退到上一帧, 又能抵消进位. 这个坑实测复现过: 第 44 帧被抽成第 45 帧, 用亮度编码帧号的测试视频可以直接验证抽帧落在哪一帧. 代价是每次抽帧都要从片头解码, 长片只对可疑锚点抽.

**33. 场景模块的段数与段落表对不上**
现象: 每段内容整体错位一段, 或最后一段被截断, 或渲染时索引越界.
原因: 改了 `script.md` 重新跑了 `timing.py`, 但没有把场景模块的 `SCENES` 列表改到与幕数一致.
规避: 渲染前先跑 `python scene_module.py segments`, 它会打印段落来源, 段数, 场景函数个数, 以及每段的起止秒与起止帧; 段数与场景函数个数不一致时直接给警告.

**34. music.py 的音区口径偏了 5 个八度, pad 与低音被低通滤光**
现象: `music.py` 出的钢琴版配乐听起来只剩底鼓与钢琴的高频叮当, pad 与低音几乎听不见, 与它 docstring 里写的"毛毡钢琴加慢起 pad 加正弦低音"不符.
原因: `music.py` 自带的 `hz()` 以 MIDI 9 为基准 (`440 * 2 ** ((semi - 9) / 12)`), 而 `dsp.py` 的 `hz()` 以 MIDI 69 (中央 C) 为基准, 两者相差 60 个半音. 和弦表按标准 MIDI 号书写 (根音写 48 表示 C3), 于是在旧口径下 `sub_bass` 被渲染到 4186Hz 后遭 260Hz 低通滤掉, `pad` 落到 4186 到 7902Hz 后遭 900Hz 低通滤掉.
实测对照 (12 秒素材):

| 口径 | 谱心 | 20 到 90Hz | 0.3 到 0.8kHz | 2 到 8kHz |
|:---:|:---:|:---:|:---:|:---:|
| 旧口径, 基准 MIDI 9 | 1166.6Hz | 54.89% | 3.28% | 12.35% |
| 修正口径, 基准 MIDI 69 | 302.1Hz | 12.55% | 4.59% | 0% |

规避: `music.py` 里用 `HZ_OFFSET = 60` 显式沿用旧口径, 保持与历史产出逐样本一致. 要修正就把 `HZ_OFFSET` 改成 0, 并重新标定母带链与低频配比, 因为 `audio-engine.md` 记录的频段目标 (低频 20% 到 40%, 温暖区高于 3%, 谱心 600 到 1500Hz) 是按旧口径实测出来的. 默认引擎 `orchestra.py` 直接用 `dsp.hz`, 不受这条影响.

## 十, 机器资源 (本轮新增)

**35. 按满核编码或渲染, 把用户开发机拖到卡死**
现象: 编码一开, 用户在同一个机器上打字都要等; 全量渲染开四个进程后整机响应明显变慢.
原因: `libx264 -preset slow` 默认按全部逻辑核起线程, 四个渲染进程各自又是单线程满跑, 两者叠加把 CPU 占满; 同时内存与磁盘写入也在抢.
规避: 重活之前先跑 `python scripts/resources.py` 拿限额, 按它给的线程数与进程数跑.

| 手段 | 作用 |
|:---:|:---|
| `assemble.ps1 -Threads <N>` | 限制 x264 与滤镜的线程数, 缺省取探测建议值 (逻辑核数除以 4, 上限 8, 高负载时再减半) |
| `-Preset` | 负载高时从 `slow` 降到 `medium`, 编码快很多, 体积略增, 用 PSNR 兜底判断能否接受 |
| `-Priority BelowNormal` | 把脚本自身进程优先级降下来, 子进程继承, 于是编码期间机器仍可正常操作 |
| `scene_module.py plan` | 打印建议的并行渲染进程数 (逻辑核数除以 4, 上限 4) 与每个进程的帧区间 |

探测还会拦两种情况: 目标盘剩余空间低于"帧序列加音频加成片再乘 1.6"的预估值, 或可用内存低于 1.5GB. 这两种情况不要硬开工, 先让用户清理磁盘或等机器空闲; 确实要开工必须显式加 `-Force` 并把理由告诉用户.

**36. 把"开工同意"当成"合成同意", 没再确认就开跑重活**
现象: 用户早就同意做这条片, 于是直接开跑全量渲染或最终合成, 结果机器当场卡顿, 用户只能要求中断, 白跑一半.
原因: 启动确认门是一次性的, 覆盖的是整条任务的代价; 而全量渲染与最终合成是仅有的两个长时间吃满 CPU 的动作, 发生在任务后段, 此时用户的机器可能已经在忙别的事.
规避: 这两步各自再走一次合成确认门. 先跑探测, 把核数, 负载, 内存, 磁盘, 建议限额与是否建议拦截报给用户, 拿到同意再动手. `assemble.ps1` 不带 `-ConfirmAssembly` 时只打印确认门并退出 3, 这个退出码的语义就是"正在等待用户二次确认", 不要当成脚本坏了.

## 十一, 引擎接口与环境差异 (本轮新增)

**37. 把相机函数传给了只吃标量的形参, 报的是看不懂的 TypeError**
现象: `python scene_module.py render 0 810` 必崩, 栈底是 `render_frame -> c.cam(cam) -> P() -> TypeError: unsupported operand type(s) for *: 'float' and 'function'`, 而同文件的 `probe` 模式完全正常.
原因: `render_range(pick, a, b, cam)` 的 `cam` 形参在引擎里被当作标量缩放值 (`c.cam(cam)` 会把镜头缩放设成传入值), 而场景模块传进去的是逐帧相机函数 `cam(t)`. `probe` 模式传的是 `cam(i / FPS)`, 也就是已经求值过的标量, 所以只有 `render` 这一条路崩.
规避: `canvas.render_frame` 与 `canvas.render_range` 现在同时接受标量与该函数, 传函数时按当前帧时间求值, 两处 docstring 都写明了. 写自己的渲染驱动时注意: 凡是"既可能传值又可能传函数"的形参, 一律用 `callable(x)` 判一下再求值, 不要让调用方猜. 见到 `'float' and 'function'` 这类类型错误, 第一反应就是查这个参数传的是值还是函数.

**38. 只装了 Windows PowerShell 5.1 的机器上 `pwsh` 根本不存在**
现象: 照文档敲 `pwsh -File scripts/assemble.ps1 ...`, 报 `CommandNotFoundException: The term 'pwsh' is not recognized as the name of a cmdlet, function, script file, or operable program`.
原因: `pwsh` 是 PowerShell 7 的独立可执行文件名, Windows 自带的是 `powershell` (5.1), 装了一个不等于有另一个, 两者不能互相替代.
规避: 把命令里的 `pwsh` 换成 `powershell`. 编码封装脚本只用 5.1 就支持的能力 (`ConvertFrom-Json`, `[Console]::IsInputRedirected`, `[Environment]::UserInteractive`, `Read-Host`, `Get-Content -Encoding utf8`), 所以两种都能跑; 脚本内不要写死 `pwsh`, 文档里两种调用方式都给出.
还要注意调用形式: **一律用 `-File`**, 即 `powershell -File scripts/assemble.ps1 ...`. 用 `powershell -Command "& scripts/assemble.ps1 ..."` 时脚本的退出码会被吞掉并统一变成 1, 而合成确认门正是靠退出码 3 与 4 表达"等待用户确认"和"探测判定应拦截", 用错形式就把安全门废掉了.
改用了 `powershell` 还有一半问题没解决: 本机执行策略会拦下未签名的本地脚本, 必须显式加 `-ExecutionPolicy Bypass`, 见第 52 条.

**39. 含中文的 ps1 在不带 BOM 时, PowerShell 5.1 会按 GBK 解码并吞掉换行**
现象: 脚本里的中文输出全是乱码; 更糟的是加长注释后直接解析失败, 报 `Unexpected token ')'`, 而同一份文件在 PowerShell 7 下完全正常.
原因: Windows PowerShell 5.1 对不带 BOM 的文件按系统 ANSI 代码页 (简体中文环境是 GBK) 解码; UTF-8 的中文字节被当成 GBK 双字节后, 字节数错位, 某些字节序列会把随后的换行符一起吃掉, 于是行被拼接, 语法就坏了. PowerShell 7 默认按 UTF-8 读, 所以看不出问题.
规避: **含中文的 `.ps1` 一律存成 UTF-8 带 BOM**. 这是本项目对 ps1 的例外规定: `.py` 与 `.md` 仍然不写 BOM (Python 3 默认按 UTF-8 读源码, BOM 只会污染 diff 与其它工具), 只有 ps1 必须带. 重写 `assemble.ps1` 时务必保留 BOM, 整体重写最容易把它丢掉.

**40. `$ErrorActionPreference = "Stop"` 下, 原生命令写 stderr 会变成终止性错误**
现象: 编码走到最后一步的响度核对时脚本直接抛错退出, 退出码 1, 后面的 PSNR 质检从未执行, 中间文件残留在产物目录里.
原因: `$ErrorActionPreference = "Stop"` 会把原生命令写入 stderr 的内容当成 `NativeCommandError` 抛出. 而 `ffmpeg` 的 `ebur128` 与 `psnr` 量测结果本来就写在 stderr, 于是必然触发.
规避: 把原生命令的 stderr 重定向到临时日志文件 (`2> $log`), 在调用前后局部把偏好降为 `Continue`, 再读日志筛行. **不要降成 `SilentlyContinue`**: 那样 stderr 会被直接丢弃, 日志文件是空的, 什么都筛不到.
同一处还有一个小坑: 筛摘要行时不要用大小写不敏感的 `Peak:`, 它会命中 `True peak:` 那一行, 把最关键的集成响度 `I` 行挤出"最后三条"; 用锚定正则 `^\s*(I|LRA|Peak):\s*-?\d` 才稳.

**41. 只做渲染前体检挡不住"中文字体键写错"的静默复发**
现象: 分镜里四个坐标轴标签, 两个图例, 标题卡日期行与片尾两行都用 `mono` (等宽字体) 画了中文, 画面上全是豆腐块; 而 `check_text.py` 全部通过, 渲染也不报任何错.
原因: 渲染前体检只检查你**主动喂给它的**字符串, 而字体键是逐处写在场景代码里的; 静态扫源码还会漏掉拼接出来的文本, 也会把从不执行的分支算进来. 一次修复之后, 后续新增的上屏文字仍然可能踩同一个坑, 属于会静默复发的缺陷.
规避: 两层一起用.

| 层 | 机制 | 覆盖什么 |
|:---:|:---|:---|
| 引擎内建回退 | `canvas.py` 的 `FALLBACK` 链 (`mono` 到 `cnb`, `cnb` 到 `monor` 等), `text()` 逐字检查并分段渲染 | 把单字救回来, 无需改场景代码 |
| 渲染期审计 | 渲染时劫持 `text()`, 收集真实上屏的 (字符串, 字体键) 组合 | 回退救不回的那些, 必须人工处理 |

审计**必须覆盖全片**: 只扫前 30 秒的实测漏了 8 处. 报告里"发生回退"是提示 (整句中文都回退了说明字体键该直接改对), "回退链也找不到字形"是交付前的阻断项.

## 十二, 内容与交付判据 (本轮新增)

**42. 画面上的数字与代码实际值对不上**
现象: 技术栏写"采样 260000", 而代码里实际是 1000 乘 240 等于 240000; 全片唯一那处"关于画面本身的陈述"正好就是对不上的那处. 这条在外部参考仓库里连续两支片子都中过, 属于流程问题而不是偶发.
原因: 数字是凭记忆或估算写上去的, 改代码时也没有回头改画面; 或者画面先写好, 代码后来才调.
规避: 交片前拿代码把屏幕上的每个数字核一遍, 对账对象与核对方法见 `content-and-rights.md` 的画面数字与代码对账. 改帧率, 改分辨率, 改采样率, 改 BPM 之后, 凡是引用这些量的上屏文字都要重新对一次.

**43. 缓动返回值被当成"这段动画播完了"的门**
现象: 逐字揭示的最后几个字永远不出现; 40 字的行稳定地少掉最后 3 个字, 看起来像"排到边上被裁了", 其实一个字都没被裁. 静默无报错.
原因: 指数型缓动饱和在 1 以下(例如 `1 - exp(-k*x)` 在 k=5 时饱和在约 0.93), 而调用方用 `if eased > 0.98:` 当完成判定, 于是那一段从来没画出来过. 一个缓动函数的返回值被同时当成两种用途.
规避: **一个缓动函数的返回值只能当一种用途**. 要缓动就缓动, 要"播完了"就另给一个线性时钟, 例如 `clamp((t - t0) / dur)`, 缓动只作用在单个元素自己的淡入上. 本项目的 `beat_on(lb, k, d)` 只承担入场进度, 不要拿它当完成门.

**44. AAC 解码后的真峰高于波形真峰**
现象: 波形文件量出来的真峰是 -2.5 dBTP, 编成 AAC 再解码回来量却冲到 0 dBFS 以上; 采样峰值定 0.84 只保证采样点不超, 编码器在采样之间照样顶上去. 实测同一段素材编解码一趟涨 3.2dB.
原因: AAC 是有损编码, 重建波形的采样间峰值可以超过原采样点; 码率越低越明显, 瞬态密集的素材(底鼓加冲击加刷子)最严重.
规避: 三条一起做. 一, AAC 码率取 384k, 不要用 256k. 二, 真峰要在 4 倍过采样之后压, 不是整体乘一个系数, 方法见 `audio-engine.md` 的混音与母带. 三, 验收必须把音频从成片里解码回来量真峰, 不能只信波形文件的数; `scripts/assemble.ps1` 已按这条打印 `True peak` 并对它下判据.

**45. 语言与用词要求只靠记忆核对**
现象: 用户要求全英文, 交付后画面里仍留着中文; 或者用户点名不得出现某个品牌, 注释里还写着旧品牌名.
原因: 靠肉眼翻场景模块, 而字符串散落在场景函数, 引擎脚本与模板骨架里, 注释往往被跳过.
规避: 用脚本扫全部源脚本与场景模块的字符串, 连注释一起扫, 扫完再交. 检查项见 `content-and-rights.md` 的语言与用词要求与 `verification.md` 的交付前自检清单.

## 十三, 排版与对齐 (本轮新增)

**46. 按字高对齐时整段文字低了一个字身**
现象: 想按大写字母的字高带把标题居中, 结果文字整体偏下, 168px 字号偏出约 147px, 看着像"锚点写错了", 其实是差了一个上伸线.
原因: Pillow 的 `font.getbbox("H")` 返回的 y 是相对**上伸线**的, 而绘制锚点 `ls` 与 `la` 是相对**基线**的; 直接拿 bbox 的值当基线偏移, 就等于少减了一个 ascent.
规避: 按字高对齐一律用引擎给的 `cap_metrics` `cap_band` `baseline_for_cap_centre` `baseline_for_cap_top`, 它们内部已经减掉 ascent. 自己算的话记得减一次, 但不要减两次. 自查方法: 把 `H` 画在 y=400, 量墨迹上边, 看它是不是等于 `400 + bbox_top - ascent`.

**47. 字号硬写导致换一个词就撑出画幅**
现象: 标题按设计稿硬写 96px, 内容换成一个更长的词以后直接顶到安全区之外, 或者换一种字体后同一字号显得又宽又松.
原因: 字号是按某个具体字符串试出来的, 而字符串与字体都会变; 字距如果写成固定像素, 换字号时松紧也跟着错.
规避: 用 `fit_size` 或 `text_fit` 反解字号, 指定"这一行要占多宽"; 字距用字号倍数(`track`)而不是像素. 反解返回上界说明目标宽度相对内容过宽, 此时该换行或缩短文案, 而不是继续放字号.

## 十四, 合成链路与脚本调用 (分批与进度)

**48. 分批切片用 `-vf select` 会把整段帧解码多遍**
现象: 8 批各 1800 帧, 每批耗时 223.3 秒, 折算下来比整段编码还慢; 又因为解码吃掉了总时间的一半以上, 测出来的"编码器速度"是失真的, 换硬件编码器只快 24%, 差点得出"CUDA 没用"的错误结论.
原因: `-vf select='between(n,A,B)'` 是在**解码之后**才丢帧, 每一批都会把整段 PNG 完整解码一遍, 8 批就白解 8 次.
规避: 切片改用输入侧的 `-start_number A` (让 image2 解复用器直接从该批第一帧开始读) 加输出侧的 `-frames:v N`. 实测同一批从 223.3 秒降到 104.4 秒, 8 批总时长从约 30 分钟降到约 14 分钟. 换编码路线之前先分离输入解码, 滤镜与编码三者的开销, 否则量到的是假象.

**49. concat 列表里的相对路径是按"列表文件所在目录"解析的**
现象: 8 批全部编码成功, 拼接那一步报 `Impossible to open 'temp\_seg\temp/_seg/seg_00.mp4'`.
原因: 列表文件在 `temp/_seg/list.txt`, 里面写的是相对工作目录的 `temp/_seg/seg_00.mp4`, 而 concat demuxer 把每一项相对于**列表文件所在目录**解析, 于是拼出了一个重复目录的路径.
规避: 列表里只写 basename (`seg_00.mp4`), 让列表与分段同目录; 这样列表还是纯 ASCII, 中文项目路径也不必额外处理. 写绝对路径也可以, 但要额外带 `-safe 0`. `assemble_core.py` 的拼接一步已经按这条实现.

**50. `-movflags +faststart` 让输出文件在整批编码完成前一直是 0 字节**
现象: 想靠输出文件体积判断编码进度, 结果批 0 编码两分钟后文件仍是 0MB, 一度以为卡死.
原因: `+faststart` 需要把 moov 原子搬到文件头, ffmpeg 会先写临时文件, 整批完成时才落盘.
规避: 不要用输出文件体积判断进度, 要独立的进度记录. `assemble_core.py` 每批原子写状态 JSON, `assemble_progress.py` 只读轮询它画进度条, 前端不启停后端.

**51. 源帧改过而没重编对应批次, PSNR 验收会假性崩掉**
现象: 单批试编与片头样片的 PSNR 都在 56dB 以上, 全片 PSNR 却只有 37.45dB, 远低于 45dB 判据.
原因: 片尾制作声明要写真实 token 数字, 该数字只能在合成前一刻统计, 于是先编码了整片, 之后又重渲了片尾 720 帧; 视频里是旧帧, 磁盘上是新帧, 这 5% 的错配帧把整片均值拉了下来.
规避: **只要源帧有任何改动, 受影响的批次必须重编**, 分批机制里的 `--redo N` 不是便利功能, 而是 PSNR 验收有效性的必要条件 (`assemble_core.py --redo N` 只重编指定批次, 再自动重拼与重混). 凡是"上屏数字依赖后续统计结果"的内容, 要么安排在最后一批渲染, 要么准备好重编该批.

**52. 未签名脚本被执行策略拦下 (第 38 条没覆盖的另一半)**
现象: 在只装了 Windows PowerShell 5.1 的机器上改用 `powershell -File scripts\assemble.ps1 ...` 之后, 报 `... is not digitally signed. You cannot run this script on the current system.`
原因: 本机 `ExecutionPolicy` 缺省是 `Restricted` 或 `AllSigned`, 会拦下未签名的本地脚本; 这与 `pwsh` 是否存在是两件独立的事, 第 38 条只解决了后者.
规避: 命令写成 `powershell -ExecutionPolicy Bypass -File scripts\assemble.ps1 ...`, 一次性绕过执行策略而不改机器设置. 文档与脚本注释里的调用示例一律用这个形式, 不要只写 `powershell -File`.

**53. 把"用 CUDA 加速"当成"给 x264 加个开关"**
现象: 用户问"合成能不能用 CUDA 加速", 于是把 ffmpeg 换成 `h264_nvenc` 重跑, 结果画面与体积都变了, 速度只快一点; 而真正的瓶颈是 PNG 解码与 `noise` 颗粒滤镜, 与编码器无关.
原因: `libx264` 是纯 CPU 编码器, CUDA 加速不了它; 用 NVENC 是**换成另一个编码器**, 编码算法, 码率控制与画质都不同, 必须重新量 PSNR. 另外 `*_nvenc` 只需要显卡驱动, 不需要单独安装 CUDA Toolkit, 所以 CUDA 版本号与 `nvcc` 都不能作为能不能硬件编码的依据.
规避: 三条一起做. 一, 换路线前先按 `verification.md` 的选型顺序分离输入解码, 滤镜与编码三段开销, 输入侧占比过半时先解决输入侧. 二, 用 `python scripts/bench_encode.py` 对比各档的耗时, 体积与 PSNR, 不要凭感觉换. 三, 探测能力一律读 `ffmpeg -encoders` 的输出 (`check_env.py` 与 `resources.py` 已经这么做了, 探测不到就明确写"走 CPU 路线", 不静默跳过).

**54. 用暗场的字符图去核验亮场画面, 整屏糊成一片**
现象: 用户指定"蓝白为主"之后画面变成白底深字, `scripts/preview.py` 打出来的字符图整屏都是 `#`, 完全看不出文字与元素位置; 一度以为渲染坏了, 其实画面是好的.
原因: 缺省模式按每个色块内**最亮**像素取色, 这是为暗场设计的; 亮场里每一块的最亮像素都是背景, 于是整屏都被判成高亮白.
规避: 亮场加 `--ink`, 它按块内**最暗**像素取色 (墨迹模式) 并按墨量给字符浓淡, 底色自然留空. 判断当前该用哪种模式: 看 `stats` 打出来的 `bright_frac` 与 `dark_frac`, 亮部占比高的片必须用 `--ink`. 两种模式都出不了结构时先查取色口径, 不要先怀疑渲染.

## 十五, 渲染期纪律 (反馈轮新增)

**55. 渲染进行中改场景源码, 成片里是旧画面**
现象: 全量渲染 (后台多进程) 进行中改了某幕的构图, 编码完成后做逐屏亮度表才发现某屏的源帧统计与当前代码应有的值对不上; 成片里是旧画面, 磁盘上却是新代码.
原因: 渲染进程吃的是**启动那一刻**的代码, Python 进程不会热加载; 渲染期间改源码, 改动既不进本次渲染, 又让"代码是对的"与"成片是旧的"同时成立, 排查时最容易被代码现状带偏.
规避: 渲染一旦启动, 场景源码视为冻结. 必须改就按固定顺序: 先停掉所有渲染进程, 改完重渲受影响幕的帧区间, 再对对应批次 `--redo`, 最后重走逐屏终检与 PSNR 复测. 铁律 22 与铁律 23 配套使用: 23 管"改了帧要重编哪个批次", 22 管"渲染中不许改".

**56. 改帧前凭幕号猜屏号, 改到了错误的幕**
现象: 逐屏亮度表显示屏 32 偏暗, 按"上一幕有问题"的印象改了那一幕的构图, 重渲重编重测全部达标, 交付后复查才发现屏 32 属于另一幕, 真正偏暗的屏从未被改到; 帧序列此时已删, 只能全量重渲.
原因: 幕内屏数不均时, 全局屏号与幕号不是线性对应, 从验收表行号往回推幕号必然出错.
规避: 改任何一屏之前先跑 `python scene_module.py screen <屏号>` 反查幕号, 幕内序, 场景函数与起止帧; 帧序列要撑到逐屏终检与全部验收通过之后才允许删 (顺序见 workflow.md 阶段 8).

## 十六, 声音分层与音频回画面 (重构轮新增)

**57. 转场音效全用噪声 whoosh**
现象: 一条 84 秒的片里放了 29 个 whoosh, 用户反馈是"一开始酷, 后来烦", 且拍点被糊掉一半.
原因: 把"每次转场配一个声音"这条纪律误当成"每次转场配一个 whoosh", 而 whoosh 是宽带噪声, 数量一多听众只听到噪声.
规避: 约一半的切点什么都不放, 由下一场的入场声 (字母 tick, 面板落位, 计数器 odo) 自己把切点带出来; 转场优先用和弦类 `swell`, 钟声 `bloom`, 滑音 `glide`, 琶音 `harp`; 噪声 whoosh 全片不超过两次, 且全片至少安排两处真实静默. `scripts/sfx.py` 跑完会自查平均间隔, whoosh 次数与最长两段留白三项.

**58. 音频包络与画面帧率不一致**
现象: 场景模块按 `env.at(frame)` 取到的包络与听到的音乐对不上, 元素起伏位置整体偏移, 不报错.
原因: 包络文件是按帧索引的 (`scripts/audio_env.py` 在导出时把 RMS 摊到帧上), 导出时是 30fps 而画面渲染成 60fps, 索引就整体错位.
规避: 取用前调 `audio_env.Env.load(path).check_fps(FPS)`, 帧率不一致它会直接报错而不是悄悄错位; 改帧率必须重跑导出, 只重渲画面而配乐没变则不必重跑.

**59. "关键句落在音乐能量变化那一小节"变成自证判据**
现象: 每次核对这条判据都通过, 但观众仍觉得音乐与内容脱节: 换一个位置去量, 曲线在那里同样有一个变化点.
原因: 本技能按画面切点分段配器并加力度弧线, 于是能量变化必然落在切点上; 先钉切点再看曲线, 这条判据只是被构造性满足, 回答不了"音乐本身在那个位置是不是真的变强".
规避: 顺序倒过来: 先合出配乐, 跑 `python scripts/audio_env.py <wav> --fps <帧率> --bpm <BPM> --anchors 6` 拿到实测相邻变化量最大的小节, 再用 `timing.py --anchor 屏号:小节号` 把关键句钉上去; 对不上就改文案或调锚点, 此时改还便宜.

## 十七, 实测反馈轮新增 (帧完整性, 版面与判据口径)

**60. 帧数全在, 但成片只有三分之一长 (阻断级)**
现象: 渲染进程被宿主强杀, 留下 `n01407.png` 与 `n03606.png` 两个 0 字节 PNG; 编码"成功"退出 0, 成片只有 1407 帧, 一条 150 秒的片子编成了 46.9 秒; 数帧数与逐屏终检都没拦住.
原因: ffmpeg 的 image2 解复用器读到坏帧是**静默停止**的, 编码器只编到坏帧就正常退出 0. 数文件个数只证明"文件名都在", 不证明"内容写完了".
规避: 两道硬闸都已内建: 编码前按字节体检帧目录 (0 字节或小于 `--min-frame-bytes` 的帧点名并拒绝开工, 退出码 8), 编码后按 `-progress` 的 frame 计数逐批核对, 拼接后再数一次 `nb_read_frames` (不等于计划帧数即拒绝进入混音). 自查命令 `python scripts/assemble_core.py --frames temp/frames_proj --probe-only`. 中断之后重跑之前必须先做这道体检, 见 `workflow.md` 阶段 7.

**61. 中文大字按字高带排纵向位置, 必然互相压**
现象: 顶杠压在主句上, 主句又压住副句, 三块连成一片; 而字符图显示构图"完整", 看不出问题.
原因: `cap_metrics` 量的是拉丁字母 `H` 的字高带 (约 0.72em), 而中文字形占满 em 框, 实际墨迹高约 1.0em. 用字高带反推相邻元素的纵向间距, 两块"刚好不相交"时真实墨迹已经压了 0.28 个字号. 字符图约 20px/列, 45 像素的重叠只差 2 列, 肉眼判不出来.
规避: `text_cap` 做单行对齐是对的, 但纵向间距一律按**真实墨迹**留, 两个中文大字块之间至少留 `0.15 x 前一块字号`; 中英混排按较高的那一块算. 编码前用 `python scripts/check_layout.py scene_module.py` 静态过一遍, 它按真实墨迹算墨迹框并两两查相交.

**62. 逐屏 p95 判据对"暗场少亮元素"的构图系统性误报**
现象: 一条 27 屏的片子里 11 屏被标记 `p95 < 120 白字不够亮`, 而逐屏字符图核对构图全部完整, 编码后观感正常.
原因: p95 是 95 分位像素亮度, 本质在量亮色像素的**面积占比**. 暗场蓝底占 75% 像素而亮字面积不足 5% 的屏, p95 天然落在底色亮度上, 与"白字不亮"无关.
规避: 判据改成 p95 与 p99 **达标其一**. `brightness.py` 现在两个都低于 120 才打印 `[不合格]`; 只有 p95 低而 p99 达标时打印 `[说明]`, 附亮部面积占比. 真不达标时先加宽主句, 再加全宽顶杠补面积, 最后才调配色.

**63. 相邻两屏用了同一个主句, 工具只出数不判定**
现象: 屏 7 与屏 8 的"与上一屏 MAE"只有 0.28, 表上没有任何提示, 逐行读表才发现; 反查确认两屏用了同一个主句"成长有三层".
原因: 逐屏表原来只打印 MAE 数值, 判定靠人看表, 而 0.28 混在一列两位数里毫不起眼.
规避: `qa.py` 现在对 MAE 加自动判定: 低于 1.0 打印 `<- 相邻屏几乎一样`, 低于 0.3 打印 `<- 疑似重复屏`, 并在表末汇总反查清单 (带 `scene_module.py screen N` 命令). 修正后该处 MAE 升到 5.61.

**64. 重渲途中跑逐屏表, 读出假阳性**
现象: 改了顶杠后启动 4 个进程重渲 9360 帧, 重渲途中跑逐屏表读出 3 屏 p95 不达标, 按纪律反查后发现屏号也猜错了, 白查一轮"为什么顶杠没生效"; 等全部渲完再跑, 三屏全部达标.
原因: 帧目录正在被重写, 逐屏表读到的是新旧混合的帧; 它是编码前最后一道闸, 假阳性会把人引向错误方向.
规避: `qa.py` 在帧序列模式下开跑前先统计帧目录里最近 60 秒被改写过的帧占比, 超过 5% 就打印醒目警告并说明"此刻的逐屏表不可信". 看到警告就等渲染进程全部退出再跑.

**65. 颗粒强度从 1 调到 2, 体积跳 20 倍**
现象: `noise` 强度只差一档, 折算每 30 秒的体积从 0.87MB 跳到 17.99MB, 直接越过 15MB/30s 的判据; 强度 4 时是 47.85MB.
原因: 编码器在高频噪点上要花的码率是非线性的, 强度 1 到 2 之间就是那条悬崖, 不是斜坡.
规避: 颗粒强度超过 1 之前先量体积: 编 240 帧量一次, 按比例折算到全片再决定给几. 实测表与口径见 `verification.md` 的体积一节.

**66. PowerShell 把 `"$AudioBitrate"k` 拆成两个参数, 混音必炸 (阻断级)**
现象: 视频编码全部完成后, 混音那一步报 `Unable to choose an output format for 'k'`, 整条流水线失败.
原因: PS 5.1 下 `"$AudioBitrate"k` 会解析成 `"384"` 与裸词 `k` 两个参数 (实测 `sys.argv` 收到 `['-b:a', '384', 'k']`), 于是 `k` 被 ffmpeg 当成输出文件名. 这不是合法的后缀拼接写法.
规避: 写成 `"${AudioBitrate}k"` 用花括号界定变量名边界 (实测收到 `['-b:a', '384k']`). 同类问题还有 PowerShell 的数组 splat: `$arr = @("-threads", "12")` 配 `@arr` 传参是**正确**的语法, 不要误改. 改动 ps1 时注意文件本身是 UTF-16 LE 带 BOM, 存成 UTF-8 会让 PS 5.1 按 GBK 读成乱码并报一堆语法错误.

**67. `check_text.py --from-source` 把 docstring 当成上屏文本, 报 462 条误报**
现象: 一个场景模块抽出 460 段文本, `cnb` 与 `cn` 通过, `mono` 与 `monor` 各报"缺字形 462 个", 字符全部来自模块与函数的 docstring (场景模块, 出代表帧做构图核对, 牌面纪律, 学术图表, 禁止发光与缩放 ...), 没有一个真的上屏; 而渲染期审计只报 1 个回退组合.
原因: Python 的 docstring 在 AST 里就是 `Expr(Constant(str))`, 与上屏文本无法从类型上区分. 同类的噪声源还有 `print` 的 CLI 提示, 报错文案与 argparse 的 help, 它们在等宽字体下必然"缺字形".
规避: 三层收紧, 按需选用. 一, `--from-source` 默认跳过全部 docstring (`ast.get_docstring` 定位), 要看全量字面量时加 `--with-docstring`. 二, 加 `--drawn-only` 只收画字调用的实参 (以及被它们引用到的模块级常量), 并把字体键一起抽出来按键分组体检, 于是"中文文案去撞等宽字体"的噪声也消失: 实测同一个模板从 164 段降到 26 段, 且零误报. 三, 项目自定义的封装 (例如 `caption` 与 `section`) 内部用什么字体静态看不出来, 默认按全部字体键体检; 用 `--call-kind caption=cnb` 声明一次即可归零. 渲染期审计仍是最后一道兜底, 两者都要用.

**68. 抽到的风格牌无法复现**
现象: 起工程时抽到一张牌, 事后没有任何记录能复现这次抽签, 只能拿 `--style <id>` 重新落盘固定; 而技能对外承诺的是"抽一张, 可复现".
原因: `new_project.py` 只在用户显式给了 `--seed` 时才把它传给 `style_lottery.py`, 不传时后者用随机种子.
规避: `new_project.py` 现在在不给 `--seed` 时自己生成一个并打印, 同时传给抽签脚本; 种子会被写进 `STYLE.md` 或 `STYLE_candidates.md` 的头部, 于是随机与可复现兼得. 手工抽签时也要显式带 `--seed`.

**69. 顶杠给矮了, p95 仍然不达标**
现象: 主句宽度已按标尺给足, 逐屏 p95 仍差一点; 凭直觉加了一道 36px 顶杠, p95 只从 54.9 涨到 110.0, 仍不达标; 一路试到 62px 才过线 (138.4).
原因: 顶杠是"补亮部面积"的手段, 面积要够才有用, 而面积等于高度乘宽度乘不透明度, 直觉估不准.
规避: 按公式算而不是试: 所需亮部占比约 5%, 顶杠高度约 `0.05 x 画幅高 x (画幅宽 / 顶杠宽)`, 1080p 满宽时约 60px; 高度与不透明度要一起给 (实测 62px 配 0.92 才达标). 公式与实测表见 `narrative.md` 的主句尺寸标尺一节.

**70. 浏览器渲染路线不可用, 只报"不可用"没有排查路径**
现象: Playwright 自带 chromium 退出码 `0xFFFF7001`, `headless_shell` 退出码 `0x80000003`, 探测只说不可用, 不知道下一步查什么.
原因: 这两个码都是宿主环境问题 (缺 VC++ 运行库, 依赖没装全, 杀软或企业策略拦了未签名子进程), 不是技能的问题, 但探测报告没有把已知的排查路径带出来.
规避: `check_env.py` 现在按退出码打印排查清单. 更要知道的是**影响范围**: 浏览器路线不可用时十阶段流程一步都不受影响, 全程用 Python + Pillow 的逐帧路线即可交付, 只有想走 HTML/CSS 出片时才需要先修好它.
