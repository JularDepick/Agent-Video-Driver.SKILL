# 结构化提示词脚手架

一条视频拆成若干阶段, 每个阶段一份提示词, 全片共用一份 `brief`. 这套分法只服务三件事: 每份提示词只说一件事, 每个阶段的产出自带检查标准, 每份提示词都能原样交给一个不了解全局的执行者.

## 为什么拆模块

- 分离的部分不会互相糊掉. 背景, 要求, 检查各自成块, 模型不会把画风建议当成任务目标, 也不会把检查项当成可选风格. 全写在一段里, 长提示词的各部分会互相稀释.
- 把为什么写进提示词, 模型才能泛化到没写的情况. 只写不要噪声镲, 换个音色库它又会用上; 写上噪声镲听感刺耳并会盖住拍点, 它会在没点名的地方避开同类做法.
- 明确点名不要什么, 比模糊的别像 AI 做的有效. 避免项要落到可判定的对象上, 例如不要全片一套配器, 不要每屏同一个入场模板, 不要文字压进画面边缘 3% 以内.
- 每份提示词对应一个阶段的一份产出, 出问题时能定位到是哪份提示词写漏了, 而不是整条任务重做.

## brief 简报

`brief` 是一个统一的 context 容器, 全片只有一份. 开工时填一次, 每个阶段做完更新一次, 把这一阶段定下的东西写进去. 模板见 `templates/brief.md`, 复制到工作目录的 `prompts/brief.md` 后填写.

| 必须装什么 | 说明 |
|:---:|:---:|
| 主题 | 一句话说清这条片讲的是什么 |
| 受众 | 谁会看, 他们预先知道多少 |
| 看完记住什么 | 一句话的收货, 后面所有取舍向它对齐 |
| 时长与画幅 | 例 108.000s, 30fps, 1920x1080, 横屏 |
| 配乐 | 音色取向, BPM, 起拍位置, 是否无人声 |
| 用户喜欢什么 | 用户点名过的参考片, 风格, 元素 |
| 用户明确不要什么 | 用户点名拒绝的做法, 原话保留 |
| 必须出现与必须不出现的词 | 例 全英文, 必须出现某域名, 不得出现某个品牌名; 逐条写清, 交付前要扫源码核对 |
| 品牌色与来源 | 做品牌片时填, 每个色值注明取自用户已有色板, 官网样式表还是产品截图; 取色方法见 `content-and-rights.md` 的品牌素材与品牌色 |
| 前面各阶段定下什么 | 风格, 配色, 段落表, 已确认的覆盖度 |
| 文件都在哪 | 文案, 分镜, 配乐, 素材, 脚本的相对路径 |

- 用户没说的地方按题材推断, 推断结果写进 `brief`, 并在汇报里问一次.
- 阶段提示词不重复 `brief` 的内容, 只写见 `brief` 的哪几项.
- `brief` 的改动与该阶段产出一并给用户看; 用户改了哪一条, 就按改后的版本重做后面的阶段.

## 每阶段提示词的七个模块

| 模块 | 写什么 | 什么时候可以省 |
|:---:|:---:|:---:|
| `role` | 这一阶段由谁做, 这个角色最在意什么 | 不可省 |
| `context` | 本阶段需要的背景, 由 `brief` 承担, 此处只写引用 | 不可省, 但只写引用不复制 |
| `task` | 产出什么, 落到哪个路径, 交付形态是什么 | 不可省 |
| `specs` | 可量化规格: 时长, 帧率, 画幅, 字数上限, BPM, 响度 | 纯创作阶段可省, 一旦有量化判据就写 |
| `style` | 推荐做法, 每条带理由; 是推荐不是规定 | 研究与渲染阶段通常可省 |
| `avoid` | 明确点名的禁区, 逐条可判定 | 有明确禁区就写, 没有就省 |
| `check` | 这一阶段算不算做完, 逐项可判定 | 不可省 |

模板见 `templates/stage-prompt.md` 的七模块表, 模块顺序与本表一致.

- `context` 由 `brief` 承担, 阶段提示词里只写见 `brief` 的哪几项, 不复制粘贴.
- `style` 里每条推荐都要跟一句为什么; 没有理由的推荐会被当成硬规定照抄, 换题材也不改.
- `check` 要写成能回答是或否的条目; 逐项清单的写法见 verification.md 的交付前的自检清单.
- `specs` 里凡是与拍表有关的数字, 都必须能由 BPM 与小节数算出来, 定义见 beat-sync.md 的三层对齐.

## 阶段与角色

| 阶段 | 角色 | 最在意什么 |
|:---:|:---:|:---:|
| 研究与事实核查 | 知识编辑 | 每一条年份, 数字, 人名, 引语都能追到出处 |
| 文案与节奏 | 短视频编剧 | 观众会不会在第一屏划走 |
| 素材与版权 | 图片编辑 | 许可是否允许这样使用, 要不要署名 |
| 风格与配色 | 艺术指导 | 全片看起来是不是同一只手做的 |
| 分镜 | 分镜师 | 每个镜头能不能在分配到的拍数里做完 |
| 场景实现 | 动态设计师 | 每个动作解释了什么, 是否落在拍上 |
| 配乐 | 编曲 | 拍点能不能听出来, 全片有没有层次 |
| 渲染 | 渲染工程师 | 帧号与时间是否精确对齐, 能否复现 |
| 验收 | 质检 | 判据是否全绿, 有没有靠想象放行 |

角色要写进 `role` 模块, 并带上这个角色最在意的那一条; 它决定这个阶段默认往哪边取舍. 阶段的先后顺序与每阶段的产出物见 workflow.md.

每个阶段的产出一律落成文件: 文案阶段用 `templates/screen-script.md` 的屏文案表, 分镜阶段用 `templates/storyboard.md` 的段落表, 场景实现阶段从 `templates/scene_module.py` 起手. `task` 模块只写文件路径与字段要求, 不重复模板里已有的表头.

## 谁来做

| 阶段类型 | 谁做 | 理由 |
|:---:|:---:|:---:|
| 需要与用户往返 | 主会话自己做 | 覆盖度, 风格, 分镜这类决定要当面确认 |
| 大而自足 | 交给子代理 | 它的上下文只装这一阶段需要的东西, 不受前面来回拉扯干扰 |

交给子代理时只给三样:

1. `brief`
2. 本阶段的提示词
3. 相关文件的相对路径

它不知道主会话里聊过什么, 所以三样都必须完整. 少给 `brief` 它会自己编受众, 少给提示词它会自选风格, 少给路径它会写错目录或另起一套命名. 拿回产出后先自己过一遍这个阶段的 `check`, 再给用户看.

## 交互纪律

- 填好的提示词与该阶段的产出一并给用户看, 不要只给结果.
- 用户改了提示词, 就从改后的版本重做该阶段, 不要在旧产出上打补丁.
- 用户没说的地方按题材推断; 拿不准的写进汇报里问, 不要默默定下再往下走.
- 用户拒绝过的做法要进 `avoid` 并留在 `brief` 里, 后续阶段不重复试探.

## 风格复刻方法

让用户给截图或录屏, 由 Agent 分析, 不要凭片名或印象猜. 分析结果按五个维度落到模块里:

| 维度 | 提取什么 | 落到哪个模块 |
|:---:|:---:|:---:|
| 配色 | 主色, 底色, 强调色的十六进制取样 | `style` 与 `specs` |
| 字体 | 衬线或无衬线, 字重, 字号层级, 行距 | `specs` |
| 运动语法 | 入场是弹出, 擦除还是打字机; 时长与缓动 | `style` |
| 转场 | 硬切, 闪白, 扫光, 溶解各自的比例 | `style` |
| 纹理 | 颗粒, 纸纹, 扫描线, 发光强度 | `style` |

- 取样要给具体十六进制与像素值, 不要只写偏冷偏暖.
- 可选的成品风格见 styles.md, 复刻不成功时把它当兜底.
- 复刻结果先做一屏试渲染, 让用户确认再铺到全片.

## 修改提示词的三个入口

| 入口 | 改什么 | 典型场景 |
|:---:|:---:|:---:|
| 改 `task` | 换内容与产出形态 | 讲三个点改成讲五个点, 一屏一句改成两行对读 |
| 改 `specs` | 换尺寸与画幅 | 横屏改竖屏, 1080p 改 720p, 字数上限放宽 |
| 补 `avoid` | 把上一版不满意的点写成禁区 | 上版转场太花, 上版文字贴边, 上版低音发闷 |

三个入口都不需要重写整份提示词; 改完在 `brief` 里记一句这次定下了什么.

## 分镜阶段的示例骨架

```
<role>分镜师, 最在意每个镜头能不能在分配到的拍数里做完, 且每个镜头至少解释一件事.</role>
<context>见 brief 的主题, 受众, 看完记住什么, 配乐; 覆盖度与文案见 script.md.</context>
<task>产出 storyboard.md, 每段一行, 字段为段落序号, 起止小节, 段内演示内容, 元素入场拍, 上屏文字. 段落边界取 SEG 数组的值.</task>
<specs>总时长 <时长>s, <帧率>fps, <画幅>; BPM <BPM>, 小节 <小节秒>s; 每段 <最短> 到 <最长> 个小节; 每屏不超过 <字数上限> 字.</specs>
<style>段落长度取 2 到 6 个小节的整数倍, 让边界自然落在小节线上; 每段内部至少一次数值或图形变化, 纯静态不超过 2 秒; 相邻两段不用同一种入场方式.</style>
<avoid>不要手写秒数当段落边界; 不要连续三段用同一种转场; 不要让上屏文字超出安全区.</avoid>
<check>段落起止是否都等于小节序号乘小节长; 元素入场拍是否写成段内拍序号; 每屏字数是否都不超上限; 切点总数是否等于段落数减一.</check>
```

填完把骨架与 `storyboard.md` 一并发给用户; 字段对齐 `templates/storyboard.md` 的段落表, 用户改了其中一条, 就从改后的版本重排一次段落表, 不要在已排好的表上局部挪动.
